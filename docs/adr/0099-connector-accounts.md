# 0099. Several accounts per connector

- Status: Accepted (built: the server, the shared client, the web and the phone app)
- Date: 2026-10-31
- Amends: ADR 0016 (the same address again replaced the account signed in)
- Code: `packages/engine/src/connectors/custom.ts` (`storeCustomConnection`, `accountFrom`), `connections.ts` (`toolPrefixOf`, `toolPrefixOfConnection`, `freeToolPrefix`, `freeLabel`, `checkLabel`, `renameConnection`), `oauth-mcp.ts` (`serverKey`), `presets.ts` (`account`), `listing.ts` (`offersCatalog`), `mcp.ts`, `access.ts`, `approvals.ts`, `agent-proposals.ts`, `tools/directory.ts`, migration `0140_connector_accounts`, `apps/server/src/routes/app/connectors.ts`, `connectors-custom.ts`, `packages/client/src/lib/connected.ts`, `apps/web/src/components/Connectors.tsx`, `ConnectFlow.tsx`, `ConnectorCatalog.tsx`, `apps/mobile/src/features/connectors/ConnectionScreen.tsx`, `ConnectSheet.tsx`

## Context

Connecting a second account of an MCP server replaced the first one's sign-in: the server found the connection by its address (`connector.custom_reconnected`), so the grants given for the first account applied to the second, and nothing said so. Two connections of one server would also have exposed the same tool names: the gateway keeps the first tool of a name, and a provider refuses a tool list with duplicates.

## Decision

1. **An MCP server takes several accounts** (one-click presets and servers by address). Its address again is another account (`outcome: connected`). Addresses match as the apps match them (`serverKey`, the apps' `sameServer`: no trailing slash, any case). `connectionId` ("Reconectar") gives that account a new sign-in or key in place, at its own address only (400 `connector.other_server`), carried through OAuth by `oauth_states.connection_id`; its name, tools and grants stay. Catalog connectors keep one connection each (GitHub's git proxy and repository list assume one): connecting again is a new sign-in (`reconnected`). A server with no sign-in, connected again, is the connection it has.
2. **The provider says which account.** A preset may name a read-only tool that lists the accounts a sign-in reaches (`account: { tool, list, id, name }`). Stripe's is `list_available_accounts_or_orgs` (`{ accounts: [{ stripe_context, livemode, name }] }`: its sign-in offers only the `mcp` scope, no OpenID, and may reach a live account and its sandboxes), not the `get_stripe_account_info` its docs name. What one sign-in reaches is one account here: its ids with their mode, sorted and joined (`account_id`), so grants given for test data never move to live money. It is asked with the fresh credentials before anything is stored, and again whenever the tools are listed (`account_label`; `account_id` is set once, and an answer for another account names nothing). The same account again only refreshes its sign-in (`same_account`). "Reconectar" signing in to another account is refused (409 `connector.other_account`) and changes nothing: the grants were given for the first one. When the provider can't say which account a Reconectar reached, it is refused too (409 `connector.account_unknown`, try again). Accounts stored before their provider was asked are asked when another account of that server comes in. An account the provider doesn't name can't be told apart: it comes in as a new one, and its name step makes a duplicate easy to spot.
3. **The label is the account's name**: "Stripe (Acme)" when the provider names it, else "Stripe", "Stripe 2"…, unique among the workspace's live connections (ignoring case). A preset's label is its English name, unique among presets ("Cloudflare (Workers)", "Cloudflare (logs)", "Supabase (read-only)"), and the apps send a catalog entry's own label, so a name nobody changed reads in each person's language, a numbered one with its number. Sign-in copy names the brand alone ("Continuar no Cloudflare"). Admins rename any kind (`PATCH …/connectors/{id}`, 1 to 80 characters, 409 `connector.label_taken`, audited as `connector.renamed` with `from` and `to`). The apps show the label everywhere (`itemName`: Conectores, the agent's page, Quem usa, approvals, the phone). The provider's name shows as "Conectado como" only when the label doesn't already say it.
4. **Tool names never collide and never move.** Each connection keeps `tool_prefix`, set once: a catalog connector's id; for a server's first account, its service's name as a slug (not the account's); a later account follows the server's oldest live account (its prefix without a number), whatever the apps send: `stripe`, then `stripe_2`. A catalog connector's id is kept only for a catalog connector this server offers (`offersCatalog`): Linear without its OAuth app leaves `linear` to the one-click server standing in for it. A partial unique index keeps it unique among the workspace's live connections; a connect that races another for it retries with the next number. Renaming never renames tools, so grants and denials of single tools keep applying. A big connector's directory is named with it (`stripe_2_find_tools`). Tool descriptions and the prompt's "What you can do" use the connection's label (a catalog connector's too), so agents tell accounts apart, and `propose_agent` finds an app by its name or by its service (`stripe`, asking for the name when two accounts match).
5. **Every account is every agent's** (as a first connection is, the ADR 0016 addendum of 2026-10-30). Connecting ends on a short confirmation that says so and how many actions ask in the chat; "Ajustar" there, or "Quem usa" on the connection's row, narrows it per agent. Tool names carry the account's prefix (`stripe_2_create_refund`) and descriptions its label, so an agent with two accounts tells them apart.
6. **What connecting did is said**: `outcome` on the connect calls, the OAuth callback (`&outcome=`) and `oauth/complete` (an older server sends none: the apps read it as `connected`), and `connector_error=other_account`, `account_unknown` or `gone` on the callback. `connector.custom_connected` and `connector.custom_reconnected` carry `label`, `account` and `everyAgent` / `sameAccount`.
7. **migration 0155** backfills `tool_prefix` with today's names (the connector id; the label's slug as `mcp.ts` made it) and numbers duplicates among a workspace's live connections (the oldest keeps its names, a catalog connector first), renaming their `tool:` and `deny:` grants with them. Duplicate labels are numbered the same way ("GitHub 2"). A deploy migrates while the previous version still serves, and a rollback runs it on the migrated database, and that version inserts connections without the column: **migration 0157** adds a trigger that fills it on such an insert as the backfill does (the catalog connector's id, else the label as a slug, numbered past the names a live connection holds), then sets NOT NULL (`-- deploy-safe:`). `toolPrefixOfConnection` keeps naming a row without one as that version did.

*Amended 2026-11-15 (personal connections):* a connection is the team's or one person's, the Vault's split (ADR 0144) that skills already follow (ADR 0020 addendum of 2026-11-14). `connector_connections.owner_user_id` (migration 0299, cascades with the person) marks a personal connection; a catalog connector keeps one live connection for the team and one for each person (`connector_connections_one_active` on `org_id, connector, coalesce(owner_user_id, '')`), and a server's accounts are told apart within each owner's (`liveAccounts`), so a person may have their own account of a service the team also has, with its own tool prefix (§4). `oauth_states.personal` carries the choice through a sign-in, which then needs only membership.
  - **Who may** (`mayConnection`, `connectionFor`, in `connectors/personal.ts`, which every route and tool goes through): any member adds a personal connection (`personal: true` on `POST …/connectors`, `…/oauth/start`, `…/connectors/custom` and `…/presets/{id}/connect`); only its person reads its details, renames, reconnects, classifies its tools or gives it to an agent. Who manages connectors sees that it exists (`?others=1` on the lists: its service, label, person and agents, no address, account, headers or tools) and may remove it or take it off an agent (`DELETE …/connectors/{id}/agents/{agentId}`, also open to who manages agents and the agent's owner); anyone else reads it as not found. `PATCH …/connectors/{id}` with `personal: false` moves the person's own to the team, when they also manage connectors. An app that doesn't send `?others=1` never gets another person's row, so an older build can't show it as the team's. Leaving the workspace revokes the person's connections and cancels what waits on them, as their mailboxes' (`dropPersonalConnections`, `cancelMailboxApprovals`).
  - **Agents** (§5 changes for these): a new personal connection goes on for its person's own agents, and an agent its person creates later gets it too. "All tools" never reaches one: only grants on that connection count, in the tool source and on the agent's page. Only its person grants it (`setAgentAccess`, `setAgentScopes`); a save that doesn't name another person's connection keeps what the agent holds of it, and `connectors[id]: false` takes it off. `request_permission`, `resolveApps`, the router's app list, `propose_agent`'s offer and `pendingConnectors` see the team's connections only; the right hand's snapshot sees the team's, and its person's own only in their own DM with it.
  - **Runs**: a personal connection serves only its own person, as a personal Vault item (ADR 0144) and a personal skill do: its tools reach a run only when the person behind it (who asked, else a routine's creator, while an active member: `vaultPersonOfRun`, through `personalUseCheck` with `ownerOnly`) is its person, and the right hand only in its owner's own DM with it (`usableConnections`). Anyone else behind the run, a teammate the agent answers directly or an admin included, or nobody, gets nothing of it: not its tools, not its name among what the run holds, not an offer to connect it. Shared channels aren't blocked for its own person. Once someone else's words reach a run (their message joins it or a run it was passed on from, `steeredByOthers` over the run's chain, or they answer a question one of those runs asked: `othersSpoke`), that run gets nothing personal for the rest of it: its tools are no longer offered and the gateway refuses a call into one with words the model passes on (`personalLostNote`). A computer brain's session a personal connection's tools were offered in is resumed only by that person's runs (`promptKey` names the persons whose own connections were offered), so what it read there never reaches anyone else's run, a mission's thread aside (Known limits). The Tool Gateway refuses a call of its tool from any other run as an unknown tool (`ToolDefinition.ownerUserId`), whatever source listed it. A card one of its tools opens is its person's alone to decide, even when they asked (`ownerApprovers` with `personal`), and Aprovações lists it only to them and to who is in its conversation (`approvers.personal`), never to admins or the agent's owner for being them. Reads are marked as from outside (`readsOutside`). Its tools carry the name others read (`auditLabel`), so what a run leaves names it by the service alone, its number kept: steps, the live chip, the task manager, the work line under a reply, a card's title, the router's list (which leaves it out) and the roster's (which names none of its grants); its person reads the whole name only on their own rows and their own cards, from the connection itself. A call in it sets no status line for the agent, which everyone who may talk to the agent reads, and a big connection's directory (`<prefix>_find_tools`, `<prefix>_use_tool`) and the run's own `find_tools` when it lists such a tool are that person's as its tools are (`ownerUserId`), so a search in them is kept in the audit and its result hidden from a run's other readers. A routine's connector trigger on a person's own connection gives its filter, inbox and the provider's error to that person only, and its event to them and to who manages connectors; anyone else reads it as a plain webhook with no address, and only its person changes it or opens its address and calls (`routine.connector_not_yours`). A widget refreshing through one shows the call it is in to its person only; anyone else reads it refreshing. Such a call never enters a task's work steps, which every reader of the task reads alike, nor the earlier steps the agent's later runs search, and the agent's list of routines gives the model of an admin's run what a member who is not the trigger's person reads. The audit log keeps such a call's input for its person alone (`personalOf`, on an approved card's run too), and a run's trace keeps only the name of such a call and its result for anyone else (`othersPersonalTools`), also while the call is still running: its step says whose connection it goes through (`personalOf`) before the audit row exists. Its writes are never kept as team actions (ADR 0064), whose record is told to anyone's run on the agent and shown under the reply, as a confidential thread's calls are not (ADR 0190). The operator's reveal door (ADR 0056) opens a personal connection, and a run's step that is a call in one, on a support request only when it is its own person's. A fault read needs no request and keeps ADR 0056's rule: the failing step of a run that failed or got stuck in a shared conversation opens whoever's connection it called, input and error included. What the agent replies in a shared conversation, everyone in it reads. Mailboxes keep their own rule (ADR 0038: the owner, or someone the agent answers directly, with the owner approving what others ask); the shared check takes `ownerOnly` for connections only.
  - **One-click through the hosted adapter**: a personal connection uses its person's own account id there (`composioUserId(orgId, personId)`), so one person's sign-in is never another's; executions still count for the workspace.
  - **GitHub stays the team's**: its git proxy, repository lists, webhooks and skill imports read the workspace's one GitHub connection (`find((c) => c.connector === "github")`), so a personal GitHub would act as the team's there. Connecting it as personal is refused.
  - **Mailboxes** were already their person's at run time (`created_by_user_id`): any member connects their own, its person or who manages connectors changes or removes it, and the list shows a person their own and any left with no person, and others' only with `?others=1` to who manages connectors, without the address. Changing someone else's (ADR 0038 still lets who manages connectors narrow it) answers with that same bare row, and the addresses it has sent from (`suggested-addresses`, read from its sent mail) are its person's alone.
  - **The audit log** gives someone else's server by address (`connector.custom_connected`, `connector.custom_reconnected`, marked `personal`) with no address and no account, as the lists do. A name that kept its default form, the service and the account ("CRM (walter@example.com)", or numbered "CRM (walter@example.com) 2", which reads "CRM 2"), goes by the service alone on others' rows (`othersLabel`) and on every audit line about the connection (`auditLabel`: its grants, its removal, a rename's `from` and `to`, a decided card's title), as a mailbox's name that holds its address does; its person reads it whole on their rows. Every other line about a person's own connection names its person (`personalOf`: the connection's sign-in, a rename, its tools' review, a change the server made to its tools, a write through it, an "Aprovar sempre" rule removed, a decided card, and the part of an agent's access save about one's own connections, kept apart as `own`): anyone else reads only its name as others read it, the agent, and what a save says of the team's, never its tools, their levels or descriptions, a card's title or a refusal's reason (`listAudit`).
  - **Who sees another person's connection on an agent**: the agent's tree with `?others=1` (`GET …/agents/{id}/access`), its grant rows (`GET …/agents/{id}/scopes`) and its mailboxes (`GET …/agents/{id}/mail`, someone else's while the agent holds it, with no rules) name it only to who manages connectors or agents and the agent's owner (`seesOthersOnAgent`). An agent's "Aprovar sempre" rules on a person's own connection (`GET …/agents/{id}/approval-rules`) are listed to that person only, since they name its tools. Names are unique among the team's connections and each person's own (`labelsTaken`), so a name never tells of someone else's. The lists of what a run holds (`connectorStates`) count the team's and the run's person's only. Widget suggestions name the team's connections only, as they are kept per agent. A personal connection that needs reconnecting is told to its person alone, as a mailbox is.
  - **Routines**: an event of a personal connection (ADR 0130) wakes a routine only when its person set the routine up (`creatorMayUse`), checked on save and again on each call, so a routine someone else set up, or one whose creator left, gets nothing. Registering its webhook at the provider is an action in the person's account: it happens only for a routine its person made (`connectorNotYours`), so a copy someone else made stays off and turning it on (`PATCH …/routines/{id}` with `active: true`) is refused (`routine.connector_not_yours`).
  - **Known limits**, left as they are:
    - Who manages routines may change where another person's routine reports (main's routine rule), and the routine still answers for its creator, so its runs keep that person's connections.
    - An agent that someone creates in a person's name holds that person's own connections at once, as one the person creates does.
    - A card a personal connection opens in a shared conversation is listed, without the power to decide it, to that conversation's members.
    - Ver passos of a routine's run in a person's own DM shows the model's own narration to who manages agents (the rule for background runs), and that narration can repeat what a tool of the person's own connection returned. So can the reply excerpt of each run in the routine's run list (`listRoutineRuns`), which who manages routines reads.
    - A mission's thread keeps one main session whoever writes (its decisions, inbox and items point at it): a teammate the mission's owner made a decider gets a turn in that session, which holds what the owner's turns read there, as with a personal Vault item.
  - **Leaving and deleting an account**: both revoke the person's connections in their transaction (`dropPersonalConnections`, never the foreign key's cascade, so the audit keeps it and the caches are cleared after the commit), and job `connector.forget_accounts` has the hosted adapter forget their one-click accounts. A one-click connection doesn't move to the team (409 `connector.move_one_click`): its account lives under its person's own id there.
  - **An agent changing hands** keeps the grants its earlier owner gave it on their own connections, and they still serve only the connection's person: its new owner gets nothing of them. Who manages connectors or the connection's person takes it off.
  - **Rolling back** to a version before this one: that version reads `connector_connections` without an owner and would serve a personal connection to every agent with a grant on it, list it to every member as the team's and replace it on a team connect. Before it starts, run `update connector_connections set revoked_at = now() where owner_user_id is not null and revoked_at is null`. Only then can the old index (`org_id, connector` where not revoked) be built again.

## Consequences

- Two accounts of one service are two rows, each with its own agents and levels, on the web and the phone.
- Only Stripe names its accounts for now: other presets get numbered names until their account tool is checked.
- A connection made before this keeps the label it was given, in the language of whoever connected it.
- No prompt rule asks agents which account a person means. Add one if agents act on the wrong account.
