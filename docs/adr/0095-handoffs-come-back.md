# 0095. Hand-offs between agents come back

- Status: Accepted (built: the server, the web and the phone app). The release waits on `bun run eval:mentions` and the hand-off cases of `bun run eval:behavior` in six languages
- Date: 2026-10-31
- Supersedes: ADR 0048 (`tell_agent` as a note sent without waiting)
- Amends: ADR 0034 (notes are tracked like questions, nothing expires while a colleague works, what an agent hands on rolls up into its answer), ADR 0053 §10 (what came of a note resumes the work for the person behind it), ADR 0089 §5 (the 15-minute rule) and §6 (where a wake-up held inside an agents' DM shows its card); by the 2026-11-23 addendum, ADR 0074 (R5's default pick) and ADR 0137 §5 (the pick for a person alone with the agents) in a channel with a responsible agent
- Code: `packages/engine/src/consultations.ts` (`tell_agent`, `closeConsultation`, `handBack`, `settleOwed`, `reportHandOffs`, `onConsultedRunFinished`, `expireConsultations`, `handOffsFrom`), `notices.ts`, `run-resume.ts` (`deliverNoticeToRun`'s `wake`), `run-inbox.ts` (`handOn`), `context.ts` ("# Work you handed off here", the prompt lines), `team.ts`, `follow-through.ts` (`wakesLater`, `FOLLOW_THROUGH_NUDGE_DM`), `executor.ts`, `stretch.ts` (`holdOf`, `peopleRun`, `continueStretch`), migration `0145_agent_handoffs`, `packages/client/src/lib/consult-group.ts`, `packages/client/src/realtime/consults.ts`, the web and phone `ConsultGroup`, `packages/engine/eval/*`; the 2026-11-23 addenda: `channel-lead.ts` (`tellChannelLead`), `router.ts`, `reply-policy.ts` (`LEAD`, `WHY_LEAD_CALLED`, `WHY_GOING_ON`), `works.ts` (`CHANNEL_LEAD_JOB`), `workspace-tools.ts` (`set_channel_lead`), migration `0340_channel_lead`

## Context

A customer's case (anonymized as in the evals): a person asked the coordinating agent, Chefe, to have Rita pass her folder and everything she knew to Diogo, because Rita was going to be deleted. Chefe handed it to Rita with `tell_agent` and sent Diogo a heads-up. Rita made a hand-off document and a zip and passed them on. While she worked, the person heard twice that nothing had happened:

- A note was sent without waiting and left no row: nothing said who had the work, and asked "então, como correu?", Chefe had nothing to read.
- Its reply came back only when a judge read it as mattering, as an `agent_note` that woke a run working for nobody, which could not hand anything on. A note that joined a run already at work lost its reply.
- Rita's own hand-off to Diogo ended in Rita's DM, where nobody read Diogo's confirmation.
- Questions expired after 15 minutes while their colleague was still working: the asker heard it was late, and its run was stopped.

## Decision

A hand-off is a tracked row. It comes back by itself, once, with what came of it, and until then the agent and the person both see who has it. No words decide anything: states come from run statuses, and the only judge calls are the existing `noteReplyMatters` and `followThroughVerdict`.

1. **Every note is a row.** Each `tell_agent` note is a row in `agent_consultations` with `kind` `note` (migration 0145: the `agent_consultation_kind` enum, `kind`, `reported_at`, and indexes on `target_run_id` and `(org_id, asker_agent_id, created_at)`; old rows are questions). The note, its row and `startOrJoinRun` go in one transaction, so a note that joins a run at work is known too. Only what a run read is its to answer: a question or note still unread in its inbox when it ends or pauses on a decision goes with its row to the run its inbox is handed to (`handOn`), and waits on no run until one takes it. It keeps the checks of ADR 0034 and 0048 (reachable agent, no note back into the conversation it answers, no cycles, `refusedAtLimit`, the same note once an hour unless the first couldn't be done or was never worked on) and adds `sameRequestRun`: no relaying what the person asked that agent directly. Notes record `chain`; `MAX_CONSULTATION_CHAIN` still applies to `ask_agent` and counts note links, and notes have no depth cap of their own (the stretch bounds them).
2. **What came of it comes back as the answer kind.** A note's result is a `consult_reply` notice (`refs.kind` `note`): the run it wakes works for the person behind the sender's run (authority follows `refs.runId`, ADR 0053), must answer, and may ask or hand work on again. A reply the judge reads as nothing the sender needs (an acknowledgement, a thanks, "nothing came yet, I'll take it when it comes") closes as reported, with no notice. With no judge, or when it fails, the reply counts.
3. **Report once** (`reportHandOffs`). The notes one run sent come back together, once none is still being worked on: queued, running, not started (held by the stretch), ended but not closed yet (its end hook still reading the reply), or waiting on what its colleague handed on. A colleague waiting on a person holds up no one: entering the wait releases the others, after the run's unread messages were handed on, and the wake names who is still out (`refs.pending`). Each close runs one claim after it commits (`reported_at` with row locks), so the last closer sees every row closed and the agent wakes exactly once. Oldest first, every notice but the last is only written (`deliverNoticeToRun` with `wake: false`); the last wakes the agent, and a run of its already at work that takes it gets the earlier ones queued ahead of it. Questions keep their own notice each.
4. **Roll-up** (`handBack`, `settleOwed`). An agent in an agents' DM that handed part of its work on and ended keeps what it owes open. Each sub-result joins that answer (`[@diogo, to whom @rita handed part of it]: …`, or "couldn't: …") in the transaction that closes it, with the agent's run locked, so no sub-result is lost to another or to the run's end. One that arrives while that agent still runs is also read by it at its next step, and joins the answer even if the run ends without reading it. Once nothing it handed on is out, what it owes closes with its reply, read from the run, then what came back. An agent that fails closes what it owes as failed at once. Nothing ever starts a run inside an agents' DM just to read a result: an unread one is dropped when the run's inbox is handed on. People read each part as "diogo: …", without the agents' marker, and not a part that couldn't be done (the delegating agent says so).
5. **No expiry while working.** Every minute, a row whose colleague is queued, running, waiting on a person or its computer, or done but waiting on what it handed on gets 15 more minutes before its deadline, its conversation hears it is still out (`agent.consultation`), and that run is never stopped. Only rows nobody started, or whose run is gone, expire as before: with what they gathered, else expired.
6. **Everyone sees it.**
   - The delegating agent reads "# Work you handed off here" every turn, like its open tasks: this agent's questions and notes from this conversation (its thread in a channel) in the last day, open or closed within the hour, newest first, at most 8, each with where its colleague is (starting, working on it, waiting on a person or its computer, waiting on agents it handed some to, not started past the stretch), the start of the answer until it heard it, and no "@" to copy. Not in routines, background runs or agents' DMs.
   - The person sees the work in the block under the reply that handed it ("Passou para 1 colega", "Chamou 3 colegas" when the turn also asked), with "O Atlas passou uma parte adiante e espera o retorno" and "O Atlas não conseguiu terminar". Notes don't take the working line (until the addendum of 2026-11-13).
   - A note's recipient now answers the person behind it: its approval, question and secret cards land where the person asked (`consultationOrigin`, `consultedFor` find note rows; the walks up a chain go 10 links), and `ask_user` works there.
7. **What agents read.** `tell_agent` says to give the whole job to the agent that owns it, with everything it needs, and not to send heads-ups to agents that only have to wait; that what comes of it reaches the agent by itself with the rest of that turn's; and, from an agents' DM, that its answer goes back once the colleague is done. "How you work" says a closed way means trying another (another tool, the colleague whose role covers it, a copy instead of a move) before saying what a person must do. The agents' DM tells a question from work, a part only another agent can do, and news of something still to come.
8. **Following through between agents.** The follow-through check also reads a run in an agents' DM that still owes an answer, with its own nudge (its last message goes back as the answer, and nothing wakes it there again). A run that handed part on gets none. `wakesLater` counts this agent's open hand-offs from this conversation, from any run, so a later "te aviso" isn't nudged while one is out. In an agents' DM it counts only the run's own: what another run there handed on goes back with that run's answer.
9. **Held wake-ups.** A wake-up `startOrJoinRun` holds inside an agents' DM posts its pause card where the people of that work read (`holdOf` places it with `peopleRun`), and the run Continuar starts takes the held question or note (its row's `target_run_id`, set in `continueStretch`, also when Continuar joins a run at work).

## Consequences

- No new kind of model call: `noteReplyMatters` runs once per note result, and `followThroughVerdict` about once more per agents'-DM run that answers a row. Fewer runs: no checks on a colleague, no unattended runs woken by note replies, no runs in agents' DMs for sub-results, one wake per turn's notes. Every wake still goes through `startOrJoinRun` or `refusedAtLimit`.
- Each run reads the block with one indexed query, and each close adds one claim statement. The block is about 400 tokens at most, only when hand-offs exist.
- A slow colleague delays the single report of a fan-out. Each part shows live in the group, anyone who asks gets the status from the block, and a colleague waiting on a person holds up no one.
- Notes sent before this keep the `agent_note` path (`noteReply`, now only for a note without a row); it can go one release after deploy. Old phone builds read notes as questions ("Perguntou a…", "espera uma resposta").
- Read-only check after deploy: `select kind, status, reported_at is null, count(*) from agent_consultations where created_at > now() - interval '1 day' group by 1, 2, 3`. Open note rows whose target run ended should be close to zero.

## Left out

- Held notes sent "after" another agent's part (`after`): giving the whole job to its owner, the roll-up, the judge and report-once cover a heads-up, and they would add a nullable message, release recursion and "not sent" states that help only when the model picks them.
- A judge call per note to read its intent: every note is tracked, so nothing needs converting.
- A "gave up" choice in the follow-through verdict: the new "How you work" line covers trying another way; add it when an eval shows agents giving up.
- A real-model eval in CI: evals stay manual (`eval/README.md`) and the release waits on them.
- Files that travel with a hand-off and move to the person's conversation when it comes back: the next step, without a migration.
- Continuar from the person's conversation for a colleague at its step limit: its wrap-up comes back as the result, and the delegating agent decides whether to hand it again.

## Addendum (2026-11-01): a mention never reaches nobody

An agent's @mention of an agent of the workspace that isn't a member of the conversation used to be plain text: no run, and only the author read about it in its next context. Now, once an agent's message is dispatched (`message.posted`), `settleReach` (`reach.ts`) settles every agent it named and didn't wake:

- **Outside the conversation**: the mention judge (ADR 0089) reads it with the members; one it needs goes as a note (`sendNote`, the delivery `tell_agent` uses), so its result comes back as any note's does. Only when the person behind the message, or the creator of the routine set to act behind it (ADR 0053 §4), may talk to that agent; a routine that only looks reaches none; an agent already in the chain or already told by this run gets nothing new.
- **Not woken for who is behind it**: a member the requester can't talk to (`dispatchMentions` now returns them as `blocked`).

Each is written on the message (`meta.reach`: agent, reason, the note's consultation, whether it was outside, whose reach fell short, the routine), drawn under it on web and phone (with Ver, Adicionar ao canal for who manages channels, and "Deixar … falar com …" for who may change the agent's audience), and read by the author in its next context. Every skip goes in the message's `routing_decisions` row with one of three reasons: `not_in_channel`, `audience`, `routine_creator_reach`. When a routine set to act couldn't reach an agent, by a mention or by its own `tell_agent`/`ask_agent` (the refusal's `data.reach`, shown under the run's next message, its report included), the agent's owner gets `agent_unreached` (once per routine and agent; who manages agents when it has no owner), opening the agent's page, with the creator in `source.userId` for a one-click "let them talk to it". The routine dialog warns, without blocking, about agents its prompt names that its creator won't reach.

A message is forwarded whole from any conversation but the agents' DM (ADR 0097's default-allow addendum; it used to be only from a public channel, with a `private` line elsewhere, which old messages still show). A target with no AI is never shown as handed (`noAi`). The router decides an agent's message before its reach is recorded, so naming an agent outside the channel doesn't stop a member from chiming in, and a `tell_agent` after a mention already handed sends no second note.

What doesn't change: who may wake whom. The limit of a routine's creator and an agent's audience stay as they were; this only makes hitting them visible.

## Addendum (2026-11-05): an ask that doesn't move ends, and a held one isn't lost

- **The loss.** A note the brakes deferred for room (ADR 0131 §7, `LATER_JOB`) had no run, so the sweep closed it after 15 minutes as "never got to it" while its wake kept looking for up to a day. The sender said the note hadn't arrived and sent it again, and the first one later woke a run whose answer went nowhere. Now a row whose wake still waits (`LATER_JOB`, `INBOX_JOB`) stays open like one with a run, and the tool's result says it waits for room.
- **The limit.** Past `CONSULTATION_HUNG_MS` (2 hours) without moving, a row ends `failed` with why: its colleague never started, or sat in its computer's line, on a computer that's away, on its plan or budget, or on its provider. A wait that ends by itself holds it longer, never past `CONSULTATION_KNOWN_WAIT_MS` (24 hours): a line on a computer that is online, a plan's limit (with a known reset, until its run's turn to resume in the plan's line (`waitingForBrain.until`) and 30 minutes, at least 2 hours; 24 hours when no reset is known). Its run or its wake goes with it, so no work lands where nobody reads it. The clock is the wait's own (`roomWaitSince`, `waitingForBrain.since`, `outage.since`), not the ask's: hours of work before one refused turn don't count. A colleague at work has no limit. One waiting on a person has none either: its card has its own 24-hour deadline (`QUESTION_TTL_MS`, `APPROVAL_TTL_MS`), after which the run goes on and answers.
- **The row's time** runs from the ask to what came back, waits included. It reads in hours past the first, and "levou 6 h" once closed.

## Addendum (2026-11-10): one row for an exchange

A few questions and notes between the same two agents within minutes drew one row per asking run, back to back ("Ada ⇄ Theo · levou 4 min", then "Ada ⇄ Theo · levou 1 min"). Now questions and hand-offs between the same two agents, either way, that overlap or start within `EXCHANGE_GAP_MS` (5 minutes) of the last one's end are one exchange (`asExchanges` in `packages/client/src/lib/consult-group.ts`): its row draws on the reply of its first asking run, shows the other agent's face and the whole exchange's time, from the first ask to the last answer, and opens one conversation with all of its parts (`useExchangeConversation`). The web and the phone share it. The other runs' replies draw no row, and an answer's notice far from that row is the one line leading to it.

## Addendum (2026-11-15): no relay wake for work that reported home itself

A hand-off whose run became a handed work (ADR 0121 addendum 2026-11-15) already posted its updates, questions and report where the person asked. Waking the sender to relay it repeated it, and with several delegates woke it once per reply.

- `reportHandOffs` still claims the turn's closed notes together, but writes each as a notice that wakes nobody when its handed work posted its result home (`agent_works.consultation_id` with `result_message_id` set). It wakes the sender once, at most, and only when one of the claimed notes ended with nothing posted home (failed or expired without a work, a heads-up). What came back stays on the record for the sender's next turn.
- A delegate waiting on a person still lets the others' results be claimed (the claim decides the wake as above).

## Addendum (2026-11-17): the agent that got the work remembers it in its DM with the person

Work one agent asks or hands another for a person happens away from that person's DM with it: in the two agents' DM, which no person reads, or in a task's own conversation when the right hand hands a task, which the person reads only by opening that task. Asked about it later in its 1:1 DM with that person, the agent that got it didn't know what they meant.

- **What it reads.** In that DM only (no one else in it, not a routine's or a background run), its prompt has "What other agents asked of you for <person>" (`handedFor`, `consultations.ts`): who asked or handed it what, when, and how it went, latest first. Its `search_context` there also reaches its DMs with other agents (not a task's conversation), keeping only messages made for that person: of the best 20 hits there, searched apart from its usual reach so other people's exchanges never take the places of what it found before. Nothing is posted in the DM: what came of handed work reaches the person where they asked (ADR 0121).
- **How it went** is the handed work's state when the hand-off's run became one, also for a note that joined that run: still on it while it runs or waits on the person, what its report said once it ended done, couldn't finish it only when the work ended that way, and "it was stopped before you finished" when a person or the agent that handed it stopped it. Continuar reopens the work, so a hand-off stopped and continued reads as at work again, then done. A hand-off with no handed work reads its own row (answered, never got to it, couldn't finish it).
- **Whose it is.** Each hand-off row records the person it was made for (`agent_consultations.for_user_id`), decided once when it is made by the rule that says whose a run is (`runAuthorityById`), wherever a row is made: `ask_agent`, `tell_agent`, and a task the right hand hands. A hand-off with nobody behind it (a routine's work) has none and is never anyone's, also when a person writes into that run afterwards. Rows made before the column have none either and are not remembered: no backfill, as the memory reaches back only 14 days.
- **How much.** The person's six newest within 14 days, read by that column (index on org, target agent, person, time): a person's hand-offs never sit behind other people's. A DM turn reads them in one statement whatever their number, and reads no run's steps: the six with their runs, handed work, reports and replies. Whether words relay outside content was settled when they were written, so nothing is worked out again on a turn. For the request it is on the row (`agent_consultations.asker_read_outside`, what the asking run had read when it asked, at each place a row is made). For the answer it is the mark the executor puts on what a run posts after reading outside content or when a routine feeds it (`meta.readOutside`): on the report of handed work, and on the answering run's reply for a question or a note. An answer whose run left no reply to say is left out; words with no run behind them are the server's own and show. A heads-up is news, not a request, and never shows.
- **What it never shows.** Another person's hand-offs (the person behind the asking run decides, as in the agents' DM). What was asked for a person stays theirs: it counts whether or not they can still open the conversation where they asked, as the agents' DM already reads for them. A request made by a run that had read outside content (the line says it relayed outside text), and an answer or report its run wrote after reading outside content (the line says it answered). Every quoted word is cut to one line and neutralised: the other agent's words read as data, never as instructions.

## Addendum (2026-11-21): a heads-up starts no work

A `tell_agent` note started a full run of the other agent, with its whole context, whatever it said. Agents that kept their teammates informed sent the same news to several agents at once, every few minutes, and each note cost a run, plus the sender's run woken by what came back.

- **`heads_up: true` works from any conversation**, not only from an agents' DM, and starts no run: the note is written to the two agents' DM, its row is closed at once (answered, reported, no run), nothing waits on it or comes back. The other agent reads it in its history there, and as "told you, as news" in "What other agents asked of you for <person>" in its DM with that person (`handedFor` now includes heads-ups).
- **The same words to a second agent in one run go as a heads-up** (`handedThisRun`, normalized as the hourly repeat check): one agent does a job and brings in the others. The sender is told so, and to hand an agent its own part in its own words.
- **What agents read.** `tell_agent` says news with nothing to do goes with `heads_up`, that most news needs no note, and never the same note to several agents; "Where you are" says the same, and in an agents' DM that a heads-up needs no reply.

## Addendum (2026-11-23): the sender goes on when a step of its own waits on the result

The 2026-11-15 addendum stopped the relay wake, and with it every wake of a sender whose delegates reported home. A sender whose own step waits on what came back (checking it, passing one colleague's result on to the next, delivering what the parts make together) got the turn back only when a person asked.

- When every note `reportHandOffs` claims posted its result home, the judge reads whether the sender still has a step only it can take (`senderGoesOn`, judgment `hand_off_next`). It reads the request the chain started from (`runChain`: a run woken by an earlier report has that report as its trigger), what the sender told the people along the chain, each note and its result, and the parts still out (`pending`). Yes when the person asked the sender to coordinate, review or approve the job or to deliver what several parts make together, when it said it would go on, when one result feeds another's part, a result asks it for something, or one failed. No for a plain delegation whose result answers the person, a check the sender offered unasked, a next step that needs a part still out, a part a person stopped (it stays stopped), a part the people can resume with Continuar (`continuableEnd`: its provider cut it off, or its step limit), and a part that failed again after it was handed again in the same stretch.
- It is asked before the claim, outside its transaction. When the claim takes another set than the one judged (a sibling closed in between), the sender wakes if a judge could have been asked. A sender still at work takes the results into its turn without a judgment (`deliverNoticeToRun` queues them on it) and reads them as news for a run already at work (`HANDED_HOME_AT_WORK`, no "woken" and no `pass`). A routine's run is never asked, nor a sender a person stopped. With no judge, or one that can't answer for this workspace or run (no Jev key and no small model, past its platform AI, a confidential thread, a workspace or agent on hold), the sender is not woken, as before. When the judge fails otherwise it is: one turn that may pass costs less than a job left half done. The restart sweep and the expiry pass the judge too.
- The wake is still one per turn of hand-offs, on the last notice, marked `refs.home`. The run reads `HANDED_HOME_GUIDANCE`, or with colleagues still out `handedHomePartly`, which names them. The results are already with the people, so it doesn't repeat them: it does its own step, hands something back only with what is wrong or missing, and otherwise calls `pass` (`replyPolicyFor` lets that run pass). Its "# Why you were called" says it was woken to go on (`WHY_GOING_ON`), not to stay quiet without looking. The stretch's limits bound the chain as for any wake.
- `tell_agent` tells the sender: not woken to relay, only when a step of its own waits on the result, and no check or step the people didn't ask for.
- The apps' line under the conversation: `agent.consulted` says `goesOn: false` when what came back woke nobody, and `stillOutAgentId` when a colleague still works on another part of that turn. The line then names who is still at it, or goes (`packages/client/src/realtime/consults.ts`), instead of saying the sender is writing.
- A colleague a person stopped while it worked: its note closes with that person's stop by name, read from the run when its worker heard the stop (`endedWhy`).
- One turn of the agent at a time. A notice, like a person's message, joins the agent's turn already open in that conversation, a channel's main timeline included (`deliverNotice` with `joinChannelRun`; who is behind each still decides, `mayJoin`): two reports that come back together wake one turn, not two acting on the same results side by side. What the agent's routine handed off for a conversation it reports to is listed in that conversation's "# Work you handed off here" (`handOffsFrom`), so a turn there doesn't hand the same work again while a colleague is on it.

## Addendum (2026-11-23): a channel's responsible agent

A channel where several agents share one job had nobody in charge of it: a question to the room got an answer from every agent, each unaware of the others, and work a person asked of one agent ended with nobody to take its next stage. ADR 0093's coordinator took unrouted messages for a whole workspace; ADR 0137 retired it as routing nobody could see on a screen. This one is per channel, shown and set where the channel's agents are listed.

- **One agent per channel, or none** (`channels.lead_agent_id`, migration `0340_channel_lead`): a member agent of a regular channel, set and taken back by whoever manages the channel (`updateChannel`, `PATCH …/channels/{channelId}` `leadAgentId`). 400 `channel.lead_channel_only` for any other conversation but a DM (which refuses every change), `channel.lead_not_member` for an agent that isn't in it; its member row is locked while the lead is saved. It is cleared when the agent leaves the channel (`removeChannelMember`, `setAgentChannels`) or is erased. An archived or held one is skipped while it is so and is the lead again when it comes back; one that answers only when mentioned takes nothing it wasn't called for.
- **What is said to the room is its** (`routeMessage`): a person's message the policy gave several agents without listing them by name gets its one answer, and a default pick (R5's best placed agent, or the pick for a person alone with the agents, ADR 0137 §5) is its. The step's own pick of the lead alone for such a message (not to it by name, not a reply to it, not a follow-up of a talk with it) is the lead's turn too. The decision's reason starts with `lead`. A message that speaks to another agent, replies to one, follows a talk with one or clearly fits one (the step's tie-break past `CLEAR_CHOICE`) keeps its pick. So does the room while the lead has a run working in the channel: the message would wait for its turn. A message of the lead's own brings no colleague in (`lead_spoke`): it asks one or hands it the work. The lead's run reads `WHY_LEAD_CALLED`: it answers once for the team, asks another agent what that agent knows (`ask_agent`) or hands it the work (`tell_agent`), and passes only when the message asks nothing of the agents. A mention of everyone that one agent answers for all (`classifyEveryone`, `one`) is the lead's when it is among them. The trade-off: a question each agent should answer about itself gets the lead's one answer; naming the agents or mentioning everyone still reaches each.
- **It gets the turn when work a person asked of another agent ends there** (`tellChannelLead`, job `channel.lead_turn`, queued by `endWork` for each ending): done or failed. Never handed work (its sender hears it through `reportHandOffs`), the lead's own work, an end people can resume with Continuar (`continuableEnd`), a failure nobody may pick up (a person's monthly limit, an archived agent, a workspace or agent on hold), a lead out of office (ADR 0084 §12), nor a confidential thread. The judge reads the channel, the work, who did it and its result (judgment `channel_lead_next`): a check before the next stage of the channel's job, a result another agent's part needs, a failure nobody picked up. An ok or a decision asked of the people stays theirs. With no judge, or when it fails, nobody is woken: no one waits on this turn.
- **What it reads:** a `channel_work` notice only it sees (`AGENT_ONLY_NOTICES`), in the report's thread and the ending run's stretch: the work's title, quoted, and the report inside `untrustedBlock`, then `CHANNEL_WORK_GUIDANCE` (`CHANNEL_WORK_AT_WORK` when it joins a run already at work). Its body is a fixed line with no handles, so it mentions nobody, and it keeps the report's `readOutside` (ADR 0117). A notice only its agent reads is no line anyone said: the router's history and a thread's last speaker (`talkingTo` in `messages.ts`) leave it out.
- **From the chat** (`set_channel_lead`): an agent a person asks makes itself (or another agent of the channel) responsible for it, takes the place of the one there, or leaves the channel with none, with that person's rights (`updateChannel`, who manages the channel). An agent outside the channel is refused with how to add it. It is a receipt with Undo (`channel.lead_changed`), and never a routine's or an unattended run's (`run-policy.ts`, `ELSEWHERE`). The right hand's `update_channel` takes `responsible` (an agent's handle, or none) the same way.
- **In the apps:** the channel's agent menu on the web (a checkbox) and the agent's screen in the channel on the phone (a switch) have "Responsible for the channel". The line under its name says so, followed by how it answers when that is a warning (it waits to be mentioned, or nothing picks for this person).

Left out: the workspace export and import don't carry it, the right hand's settings card has no row for it, and an archived lead can be replaced but not cleared from the apps.

## Addendum (2026-11-24): the agent in the middle goes on when what came back needs it

An agent answering another agent in their DM that handed part of the work on (a check, a fix, another part) ended its turn, and when the result came back it only rode up inside its answer (decision 4). The agent in the middle never acted on it: a check that found problems in its own work went up to the agent above, which had not done that work, and the fix waited until someone asked again.

- **Once everything it handed on is back** and its run already ended still owing an answer, one judge call (`handed_back_next`, `goOnBetween` in `consultations.ts`) reads the request, what it said and each result, and asks whether a step only it can take is left (fix what a check found, check again, put the parts together, pass a result on, a part that failed and nobody picks up). Yes: a notice in that agents' DM wakes it once, its run there takes what it owes (`target_run_id`), and that run's reply goes back with the results (`settleOwed`, as before). No: its answer goes back as before.
- **No judge, or a judge that can't answer** for the workspace or run (no Jev key and no small model, platform cap, confidential thread, a hold): no wake, as before. Other judge failures wake. Past the stretch's limits (ADR 0089) it isn't woken either: the answer goes back as before, with no pause card for a run nothing would wait for.
- **Nothing is lost on a failure:** a run that fails or is stopped while owing an answer closes it as failed with why, followed by what its colleagues had sent back.
- `tell_agent` from an agents' DM says the agent is woken there first when what comes back needs a step from it.
