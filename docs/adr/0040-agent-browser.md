## Context

ADR 0031 plans four kinds of screen. The browser carries most of the value (web apps without an API, test logins, Stripe test checkouts, checking a UI the agent just built) at the least risk. We take it first, on connected computers only.

### `agent-browser`

ADR 0031 §4 planned to drive Chromium over CDP ourselves. A tool already does that for agents: **`agent-browser`** (Vercel Labs, Apache-2.0, `github.com/vercel-labs/agent-browser`).

- A native Rust CLI and daemon, one daemon per session, speaking CDP directly to an installed Chrome (or Chrome for Testing it downloads). No Node, no Playwright. About 20 MB per platform.
- `snapshot` returns the page's accessibility tree as text with refs (`button "Submit" [ref=e2]`); actions take a ref (`click @e2`, `fill @e3 "…"`); a click covered by another element fails with the covering element named. `wait --text/--url/--selector/--load`, tabs, frames, dialogs, upload, console, network, `screenshot` (`--if-changed`).
- Per session: `--session`, `--profile <dir>` (persistent: cookies, storage, cache survive restarts), `--allowed-domains` (also blocks sub-requests, WebSocket, beacons, WebRTC), `--content-boundaries`, `--max-output`, `--action-policy`, idle shutdown.
- A local WebSocket stream per session: JPEG frames with viewport metadata and URL changes out; `input_mouse`, `input_keyboard`, `input_touch` in; fps capped per client; newest frame wins.
- It calls no model (an optional `chat` command through Vercel's AI Gateway is not used). The page is text, so any model drives it, including models without image input.

### How others do it (checked 2026-10-19)

| Product | Live view | Take over |
|---|---|---|
| OpenMausBot (Apache-2.0) | Relays `agent-browser`'s JPEG stream; noVNC for full container/VPS computers | A person's "hold" pauses the agents and survives a dropped stream for a while, so the panel reconnects and carries on |
| OpenBot (CopilotKit, MIT) | Screenshot polling while watching; Chrome's CDP screencast (JPEG) over a WebSocket while a person drives, input back over CDP (after DevTools' `InputModel.ts` and Steel's casting handler) | Command mapped to Control, paste forwarded |
| Steel | Headful: WebRTC H.264 at 25 fps from the OS display. Headless: CDP screencast, called legacy | `interactive=true` on the viewer |
| Kernel | WebRTC adapted from neko, or noVNC. Fixed resolution and capped fps because 1080p dropped frames | Read/write by default; pauses recording while a person types sensitive data |
| Browser Use, Anchor, Hyperbrowser | An iframe with a live URL (a bearer token) | The iframe is interactive; the embedding app locks it |
| Cloudflare Browser Run | Live view URL | A formal handoff: `handoff(instructions, timeout)` → the person picks Done or Failed → `handoffComplete { success, reason }` → the script resumes |

Conclusions: headless browsers stream JPEG frames; video (WebRTC) appears only where a full display is captured. The two products closest to ours (OpenMausBot, OpenBot) use JPEG for the browser, and OpenMausBot uses `agent-browser`. Cloudflare's handoff is the clearest shape for "the agent needs a person".

Lessons from OpenMausBot's code (`server/browser-relay.ts`, `server/browser-live.ts`):

- The daemon runs one command per session at a time: a read waits behind the agent's command, and a timed-out command stays queued.
- Some commands relaunch a Chrome that died; check `stream_status` before reading.
- The stream's `input_keyboard` lacks virtual key codes and text for Enter/Tab; complete them with `agent-browser`'s own key resolver.

### Alternatives considered

- **Our own CDP code:** weeks of work `agent-browser` already did; kept as the fallback behind our tools.
- **Video (H.264 through ffmpeg's WHIP output to LiveKit or Cloudflare, or WebRTC):** lighter on the wire, but an extra binary, an experimental muxer, a media service (inbound UDP, which not every host offers) and players on web and phone. For a login of a few minutes, JPEG at 10–15 fps is close enough.
- **DOM replay (rrweb):** very light and sharp for watching, but logins live in cross-origin iframes (Stripe, Google, captchas), OAuth opens popups, assets load from the viewer's browser without the agent's cookies, and clicks on a replica are fragile. Not for take over.
- **A visible window on the computer for logins:** dropped; one path everywhere (the stream).

## Decision

### 1. `agent-browser` behind our own tools

- The runner drives `agent-browser` (pinned version) as a child process with `--json`. Agents never get the raw CLI or its MCP server: they get our tools, so Stop, the allowlist, secrets, handoff and caps hold whatever the brain.
- Our tools are the interface: if `agent-browser` changes course, our own CDP code replaces it under the same tools.
- Turned off on our side: its credential vault (secrets come from `request_secret`), importing auth from the owner's Chrome (`--auto-connect`, Chrome profile reuse), `chat`, plugins, its dashboard.

### 2. Shipping

- **Desktop app (macOS):** a second Tauri sidecar next to `agentes-runner` (`externalBin`). CI downloads the pinned release, checks its SHA-256, signs it with our Developer ID and notarizes it with the app. It updates with the app.
- **Terminal installs (servers, Linux, Windows):** the runner downloads the pinned release from GitHub into `~/.agentes-runner/bin/` and runs it only when its SHA-256 matches the one pinned in the runner (integrity comes from the pin, not from where it is served). Machines whose browser is off download nothing; with it on, a runner outside system mode gets it as it starts (§11).
- **System mode (`install.sh --system`, x86_64; added 2026-10-30; Chrome superseded by ADR 0133, which installs Google Chrome stable from Google's apt repository instead):** the installer puts the pinned `agent-browser` and a pinned Chrome for Testing build in `/opt/agentes-runner/browser`, root's and run by every agent's user, each checked against its SHA-256 before it is installed. Both pins live in the installer, so a fleet that checks the installer against its own SHA-256 before running it pins them too. The runner uses that folder only when nobody but root (or its own user) could have written it or its `agent-browser`; it never writes there, and installs nothing per agent then. Chrome keeps `agent-browser install`'s layout (`chrome-<version>/chrome-linux64/chrome`), which the user agent's version is read from. A new pin keeps the build installed last before it, for a runner not restarted yet, and removes older ones. `agent-browser install` (0.39.1) pins no build: it takes the Stable channel of the day it runs, so agents that installed their own on different days ran different Chromes. The installer's pin is a Stable build checked once by hand: Google publishes no SHA-256 for these zips (only MD5 and CRC32C), so a new pin is the zip downloaded once, its SHA-256, and its MD5 compared with the bucket's. The first pin, on 2026-10-30, is 156.0.8078.80. Without a pin the installer puts only `agent-browser` there, and each agent installs Chrome at its browser's first use. A download that doesn't match its pin stops the install; one that fails (the network, say) only warns, since the runner falls back to installing per agent what the folder lacks.
- **Chrome (superseded by ADR 0133: the computer's own Google Chrome stable, updated like anyone's, no Chrome for Testing):** always Chrome for Testing: the newest by version of the shared install's (above) and the one `agent-browser install` puts in the user's home, installed there only when there is neither, with progress on the machine page; never the person's own Chrome (its updater rewrites the app while we hold it open, and macOS blames our app). Linux without Chrome's libraries needs `install --with-deps` (sudo): the runner doesn't report the browser and the machine page shows the command.
- **Started by the runner, attached by `agent-browser` (`--cdp`):** the runner launches that Chrome itself (headless, `--remote-debugging-port=0`, the agent's profile, no `--enable-automation`, `--disable-blink-features=AutomationControlled`, a normal user agent for its version) and every command connects to it. Measured on a Mac (2026-10-19): a Chrome `agent-browser` launches carries the automation markers (`navigator.webdriver` true, "HeadlessChrome"), and Google's sign-in answered "this browser or app may not be secure" while its search went to /sorry ("unusual traffic"); the same Chrome started by the runner and attached reached the account check and the results. This doesn't make the browser invisible to sites' own rules: a CAPTCHA or a "verify you are human" goes to a person through the help request (§6), never solved by the agent, and sites that forbid automated use still do.
- The license and NOTICE go in the app's about box and the runner's `licenses` output.

### 3. Turned on in two places

- **On the machine:** a fourth switch in `access.tools`, `browser`, set by the person on the computer (tray app or `agentes-runner access`), off by default. As with the other switches, the server can show it and ask to turn it off, never on. `hello.browser` reports whether the computer can serve it, whatever the switch (the switch itself travels in `access.changed`, so turning it on needs no reconnect).
- **On the agent:** the scope `browser:use`, outside "all tools" (like `sandbox:run`), on the agent's page next to its computer. Offered only when the agent's computer reports `browser` on; disabled with the reason otherwise.

### 4. One browser per agent, logins kept

- Session `agent-<id8>`, persistent profile and downloads in the agent's folder (`<handle>-<id8>/.agentes/browser`), headless, idle shutdown after 15 minutes. A login done once stays until the site ends it.
- The runner owns the Chrome process: it stops it after the idle time (not while a person watches or a help request is open), on `browser.stop`, on the agent's `close` and when it stops; a read never starts one. Pids go in `<runner home>/browser/chromes.json`, so Chromes a crashed runner left are stopped on its next start (only when the pid is still that Chrome on that profile).
- Per agent, not shared: another agent signs in on its own. Per computer: an agent moved to another computer signs in again.
- On a computer with the agents' desktops, the same Chrome and profile also open from Browser on the agent's desktop (ADR 0058 §7, added 2026-10-25): a person in control who signs in to a site there signs the agent in. The click brings no address; a page a person leaves it on is checked against the site list below before the agent reads it, as a page that moved by itself is.
- The agent signs in to whatever account the person tells it to: it types a password only when it was given one through `request_secret`, otherwise it asks the person (§6). No rule about which accounts; the agent's page says only "The agent stays signed in to the sites it enters, on this computer". Real payments, deletions and sending on someone's behalf still go through an approval. Until protected mode exists, other unprotected agents and the owner can read that folder.
- Optional site allowlist per agent, enforced by the runner: `agent-browser`'s `--allowed-domains` refuses persistent profiles, so the runner checks a navigation's URL before it goes and the page's URL after every action (going back when it left the list). Top-level pages only: sub-resources aren't filtered. `file://` and the owner's paths blocked.
- Cap of live browsers per machine (owner setting, default from memory, about 300 MB each); over it the agent sees "waiting for the computer".
- The runner serializes commands per session (one at a time, like the daemon), times them out and checks the session before reading.

### 5. Tools

Named `browser_*` (the `computer_*` names are the Daytona lifecycle):

- `browser_open(url)`, `browser_back`, `browser_tabs` (list, open, switch, close)
- `browser_read` → the snapshot as text with refs, wrapped as untrusted content, capped in size
- `browser_click(ref)`, `browser_fill(ref, text)`, `browser_select(ref, value)`, `browser_check(ref)`, `browser_press(key)`, `browser_scroll`, `browser_upload(ref, file)` (a file from the agent's folder)
- `browser_type_secret(ref, secret)`: types a secret already delivered with `request_secret`; the runner reads it locally; refused when the target isn't a password or one-time-code field
- `browser_wait(text | url | selector | load, timeout)`
- `browser_screenshot`: saved in the agent's folder (Claude Code and Codex read it there), always as a `.png`, since agent-browser's `screenshot [selector] [path]` reads a lone name without a slash or an image extension as a selector; image results for gateway brains come with ADR 0031 step 2. With `share`, the same call also sends it to the Drive the way `upload_file` sends a file (ADR 0025 §4) and its card goes with the reply; that takes Write files (`drive:write`), never Run code, and without it the image stays saved and the answer says to ask with `request_permission`
- `browser_ask_person(instructions, timeout)`: the handoff (§6)
- `browser_close`

Refs go stale after navigation; the tools say so (`stale_ref`) and the agent reads again. Every brain gets the same tools: gateway brains through the Tool Gateway, Claude Code and Codex through the runner's `agentes` MCP bridge.

### 6. Handoff: the agent asks, a person does it, the agent checks

Modeled on Cloudflare's handoff:

1. The agent calls `browser_ask_person("Sign in to Stripe with the shop's test account")`. The run suspends, like `request_secret` and approvals.
2. A card in the chat ("Dev needs you · Sign in to Stripe · Open"), at the top of "Waiting for you" in notifications, and a push to the phone. It goes to both the person who asked for the work and the agent's responsible person (once when they are the same); the first to open takes control, the other sees "Ana is helping". *Amended 2026-11-04:* only to those of them whose roles give them the agents' browsers (`own_browsers`, ADR 0085 §12); asked of neither, it waits for whoever may use every agent's browser (`control_browsers`).
3. The person opens a full-screen live view (§7) with the agent's instructions on top, a "you're in control" badge, and two buttons: **Done** and **Couldn't**, each with an optional note. The agent reads every note; the card and the conversation's events carry only Couldn't's (the card shows it).
4. The agent resumes with `{ result: done | failed | cancelled | expired, note? }` and the facts of the person's turn (below), reads the page again and checks the outcome (still on the login page → it says so in the chat instead of carrying on). The card resolves itself.

A person watching can also **take over** on their own, while the agent may use its browser (`browser:use`, §3; 403 otherwise): the same screen; the agent pauses and, when handed back (**Hand back**, with an optional note), is told a person used its browser, with the same facts, and reads again before acting.

- **Facts, not a diff:** what the agent reads on resume says who had control, for how long, the page (address and title) when they took it and when it ended, and their note, quoted and marked as the person's own words. The pages come from the live view's newest frame, else a quick `get url` on the computer; they are kept in memory only (like the frames), so after a restart or on another replica the text says less. The site's title is quoted as data, never instructions.
- **A person can open a site** while in control (`POST …/agents/{agentId}/browser/open {url}` → 204): only the person in control (409 `browser.not_in_control`), only while the agent may use its browser (`browser:use`, §3) and its computer serves it (403, the same checks as its tools), http(s) only (a bare host gets `https://`; anything else 400 `browser.bad_address`), and the agent's site list holds: the runner checks it as for the agent's own `open` (403 `browser.not_allowed`). A closed browser opens (the runner starts Chrome), so a person can open the agent's browser from its page to sign in before giving it work; the live view starts its stream at once (`browser.opened` on the handoff topic). A page that fails to load is 400 `browser.open_failed`, and Chrome's error page shows.
- Taken from a run's card, the take over is bound to that run (`runId`): its card stays in that run's conversation (on the run's last message, else at the end) while the person holds control, even after the run's live block goes, and `browser.handoff.updated` goes to that conversation. Taken from the agent's or the computer's page it has no run until a run's browser call waits on it; the tray links to the run's conversation, else to the agent's page with its browser open (`/org/{orgId}/agents/{agentId}?browser=1`).
- If the run under a take over ends (done, failed, canceled) while the person keeps control, the person keeps the browser and the card stays; the agent's next run that needs the browser takes the take over over (it waits on it, and the card moves to it), so it is never "busy" forever. A run still going keeps it (other runs are refused).
- Leaving without handing back (expired) is told to the agent as such, not as handed back. "Parar" is heard by everyone watching (`browser.stopped` → `browser.ended` with who and when).

- One person in control per agent browser. While someone is in control only they get frames (at the control rate): the other viewers' `browser.status` says `hidden` and who is in control ("Ana is in control · screen hidden"), and they get the page again, the newest frame at once, when it is handed back. What a person types in the agent's browser isn't watched by others.
- Handoffs are kept per screen of the agent (`browser_handoffs.screen`, `ScreenKind`; the browser's is `browser`): one open handoff per agent and screen, so another screen's handoff neither blocks nor hides the browser. The agent's routes exist per screen (`…/agents/{agentId}/{screen}/handoff`, `…/takeover`, `…/stop`); a handoff's own routes (`…/browser/handoffs/{handoffId}/…`) serve every screen. People may drive a screen only while the agent may use it (the desktop's `desktop:use` is never covered by "all tools").
- Timing: a request waits 24 hours for someone to open it (the agent may ask for less), its browser held open all along, then expires (it was 10 minutes, up to 30, as in OpenBot and OpenMausBot; people often see a request later, and an open browser costs a computer paid by the month nothing more). Still unanswered an hour after it was asked (nobody pressed Done or Couldn't, canceled or took control), the people it was asked of are reminded once: their notification comes back unread and their phone hears "Ada still needs you in the browser" (job `browser.handoff_remind`, an outbox job due at that hour that does nothing once the request ended); once a person is in control there is no deadline; if their view drops, control is kept for 2 minutes (presence renewed every 30 s and stored in the database, so it holds across replicas and restarts), then it ends as `expired`. Presence is a view showing the page: a view whose page never came (its first frame never arrived) neither renews control nor pushes it on leaving and watching again, so that control ends 2 minutes after it was taken and the agent goes on.
- While a request is open (waiting or in control) the agent's browser tools wait or refuse; after a person had control, only `browser_read` (or `browser_open`, for a browser that closed meanwhile) works until the agent reads the page again (`page_read_at`, migration 0080), as OpenBot requires a fresh snapshot after hand back. The refusal repeats the facts of the person's turn. Couldn't from someone who never took control changed nothing on the page: nobody is recorded in control (the agent reads only who answered).
- The agent may restart its browser during a person's turn (`browser_close`, then `browser_open`) when the person using it asks: from the run the turn is bound to, or a run of the person whose turn it is (in control, or asked). The open request or take over ends as `cancelled` with nothing to read first, another run waiting on it is told why, and where its card is the conversation gets "Ada restarted its browser. Ana's control ended." (when a person had control). Any other run's `browser_close` waits or is refused, as every browser tool. The run that ended the turn itself never hears of it later: the sweep resumes only runs still waiting on a handoff that ended.
- The agent's browser stays alive while a request is open (the server keeps the session active so the 15-minute idle shutdown doesn't close it).
- Who may watch: org admins, the agent's owner, the people the request went to and whoever asked for the work; a channel reader can't. Who may drive it (take over, take a request, type and click, open a site) is narrower (`requireBrowserControl`): org admins, the agent's owner, and the person an open request was asked of, only while it stays open. Whoever asked for the work only watches: the agent's one profile holds the logins other people gave it, so talking to the agent must not lend them. Cancelling stays with the person in control, the one asked, the owner and admins. Access is checked again every 30 s while watching, and control before each input. The apps ask `GET …/agents/{id}/{screen}/control` (`canControl`) and show Assumir only to who may drive.
- Nothing reaches the model during a handoff: no frames, no keys.
- Passkeys and hardware keys don't cross a remote view; the person picks another sign-in method.
- We never copy cookies from the owner's own browser.

**Addendum (2026-11-03).** The hand-off is how the agent goes on, not a last resort: `browser_ask_person` is described as handing the person the step only they can do (sign in, scan a QR code with their phone, type a code sent to them, solve a captcha, confirm on their phone), after opening the page and getting to that step, and never a reason to stop or to say it can't. The browser guidance says the same, and a service with no connector but a web version is used in the browser, the person signing in (ADR 0097, addendum 2026-11-03).

### 7. Live view: `agent-browser`'s JPEG stream, in memory

- The runner opens the session's local stream only while someone watches and forwards frames over its machine socket, with the active tab's address and title. The server relays them to the viewers' sockets in memory: nothing written to Postgres, nothing stored.
- Adaptive: up to 5 frames a second while watching, 15 while a person is in control, 1 for a small thumbnail (§7.1). Chrome only sends frames when the page changes; newest frame wins, stale frames are dropped.
- **First frame:** Chrome sends no screencast frame for a page that isn't repainting, and `agent-browser`'s stream only replays a frame it already has (checked in 0.39.1's source: its own recordings seed a screenshot for that reason). So a new stream with no frame after 1 s gets one JPEG screenshot as its first (through the session's command queue), and the relay holds the newest frame of a running stream in memory: a viewer who joins, or whose view stops being hidden, sees the page at once. An idle open browser shows a picture, not a spinner. A start on a stream already running (a server that lost the page: a new process, a stop that failed) sends that screenshot again, and every view that starts sends `browser.watch` (a second view on one socket never heard the answer to the first).
- **Reconnects:** when a computer says hello again (its runner may be a new one, whose hello came before the old socket's close), the server forgets the stream and the frame it had for its agents and asks for the stream again at once; a closed browser says so. A view that waited 75 s for a page (opening, reconnecting, not available) says it couldn't open the browser, with Try again (§9). It counts only while it watches on an open socket: a card off screen, or an app without a network, isn't waiting on the browser. A watch the server refuses because the socket already watches 4 browsers says so instead, and is tried again with backoff.
- **Closed:** a stream can't start on a closed browser (never opened, idle shutdown, Stop, the agent's `close`): the runner says `browser_closed` and viewers get `browser.unavailable` with reason `closed` (an older runner's `bad_request` stays `unavailable`, with its message). The app keeps watching with backoff (up to 10 s), so the view shows the browser once something opens it (the agent, or a person in control opening a site, which also restarts the stream at once). No frame is kept for a closed browser: the app shows that it is closed, and that logins stay.
- Input from the person: mouse and touch as stream input events (coordinates mapped from the displayed frame to the page); special keys as key events, completed with `agent-browser`'s key resolver; Command mapped to Control where the shortcut expects it; paste forwarded. Pressing, dragging and fingers: §14.
- **Typing through a native text field:** the app shows its own text field (secure for passwords) and sends the whole text into the focused page field (`keyboard inserttext`). Accents work, and the phone's and password manager's autofill fill it.
- Popups and new tabs (OAuth windows) followed: the view switches to the active tab.
- The viewer reconnects by itself (backoff), so a deploy (`overlapSeconds`) or a network drop shows "reconnecting…" and carries on.
- The relay sits behind a small interface of ours (`StreamRelay`), in memory today. Frames come from a `FrameSource` (JPEG today).
- Load: the server only copies bytes. About 25–50 KB per frame; a 2–3 minute login is about 30–75 MB; nothing while nobody watches.

#### 7.1 Sockets of its own, paced by who watches (2026-11-05, runner protocol 49)

The live view lagged, most of all while a person drove the page. Nothing bounded how far behind it could fall: in control the runner forwarded up to 15 frames a second as base64 JSON on its machine socket and skipped one only once 2 MB were waiting there, and the server skipped a viewer's frame only once 1 MB waited on that viewer's realtime socket. A computer's upload that took fewer frames than that queued seconds of pictures, which the person watched replay after each click; and every command, result and chat event waited behind them on the same sockets.

The design: each hop carries the pictures on a socket of its own, as bytes, and every hop sends a new picture only when the next one down has room for it (`BROWSER_VIEW`). A slow link anywhere then shows the page as it is now, never the seconds it fell behind, and a computer sends nothing nobody can take.

- **The source.** The runner opens `agent-browser`'s stream with `pacing=ack`: the daemon keeps only its newest frame and sends one when the runner acknowledges the last. The runner acknowledges at once when the frame went on, and otherwise only when the view has room again (in system mode root tells the agent's worker, which runs the browser, with `browser.room` on their link), with a 2 s safety ack so a lost message never freezes it. Frames are JPEG at quality 60, at most 1280 pixels on each side (a high-density screen's frame is scaled down to what a panel shows), and carry their capture time (`capturedAt`) to measure how late pictures arrive. Watching asks for up to 5 frames a second (it was 1, which read as frozen while a page loaded or scrolled), control 15; Chrome still sends one only when the page changes.
- **Computer → server: the view's data socket.** Before `browser.stream.start` the server sends `browser.view.open` with a fresh `streamId` (only to runners at 46, only where the machine's socket is on this replica). The runner's own process dials a data socket for it, as a desktop's (`/api/machines/stream`, `stream.hello` with the machine's token): in system mode that is root, the only process with the token, which already passes its workers' frames up (`BrowserViews`, `OP_ROUTES` "machine"). That agent's frames go there as bytes: a version byte, the header's length, a JSON header (`seq`, the metadata) and the JPEG (`encodeBrowserFrame`). The broker hands a data socket naming no stream of its own to the live view (`StreamBrokerDeps.claim`). At most 3 frames are on their way unacknowledged (`BROWSER_VIEW.window`: enough for 15 fps over a ~200 ms round trip, at most a fifth of a second of pictures queued); the newest waits in place of older ones. The server acknowledges a frame at once when someone watching here has room, and otherwise owes the ack until a viewer frees room, at most `ackOwedMs` (2 s). A full window with nothing draining for `stallMs` (5 s) means the socket is dead: the runner ends the view (close code `viewTooSlow`, 4413: Node's WebSocket client refuses 1013), hands its newest frame to the machine socket at once, sends the rest there as `browser.frame` as before, and the server opens a new view with backoff (1, 3, 10 s; a view closed as too slow keeps its backoff); the newest frame also starts the next view, so an idle page always shows its current picture. Until a view's socket is there (the first frames of a stream) frames also go on the machine socket. The server drops a machine-socket frame no newer (`seq`) than the newest its views brought: a straggler; a newer one means the runner left its view, even if that socket's close never arrived (a half-open link), so the server ends the view, shows the frame and opens a new one. Older runners and servers keep the old flow.
- **Server → each person: a frame socket and a window.** A client that watches with `acks` and `frames` gets `{"type":"browser.frames","agentId","ticket"}` and opens `GET /api/browser/frames?ticket=` (single use, 30 s, for that view; it needs the same replica as the realtime socket, like the desktop's streams). The server sends that view's pictures there as bytes (made once per frame for every viewer, `browserFrameBytes`) and the client answers each one with `{"type":"ack"}` once drawn. The socket stays open across re-watches of the same agent, is closed only by an unwatch or the realtime socket closing, is pinged every 30 s, and when it drops on its own the client asks for a new ticket (`browser.frames.renew`, waits of 1, 2 and 4 s). Each person has their own window of 3 (`createViewerPacer`), and a frame socket that closes frees it at once: a phone on mobile data never slows the others or the computer; a hidden tab, which draws nothing, gets the newest picture every 5 s. Frames on the realtime socket (before the frame socket opens, or without one) carry `ack: true` and are answered with `browser.ack`; a client acks only frames that say so, so an older server never hears an ack. A JSON frame older than one already drawn from bytes is not drawn (by `seq`, or by capture time when the stream started again); a newer one with `ack` means the server left the frame socket, which the client then drops and renews. Pictures still arriving on the frame socket after `browser.ended` or `browser.unavailable` are acked but held until the next `browser.status` (then drawn) or a new watch (then dropped), so a late picture never undoes an ended view. Messages that aren't pictures never wait, and one that ends or hides the view drops the picture waiting. Sends that Bun drops, or a frame socket with over 1 MB waiting, take no room in the window.
- **A rate per view.** `browser.watch` may carry `maxFps` and `browser.fps` changes it in place (1–15; 15 or none is no extra limit). A socket asks for the highest rate any of its views of that agent needs: the phone's closed card and its peek of a request ask for 1, an open view and the web's cards for the stream's own. A server that has shown it paces (a frame with `ack: true`, or a ticket) is the only one told `browser.fps`. Apps from before this send no acks: they get the newest frame once a second while watching and the stream's own rate while they drive it, as before.
- **Drawing.** The web shows a frame's bytes through a `blob:` address in the same `<img>` (`LivePicture`, which owns the image and frees each address once the next one has loaded), so the browser decodes it off the main thread, no 70 KB base64 string passes through the page per frame, and the card around it doesn't re-render for each one; the layout and the click mapping are unchanged. The phone keeps base64 on the realtime socket (`browserFrameSockets: false`): React Native hands binary messages to JavaScript as base64 anyway, so bytes would cost it two extra passes per frame. Drawing bytes natively (Skia) would let it move to the frame socket.
- **On the agent's screen** (2026-11-05): where the browser runs on the agent's desktop and the person may watch it, the card shows that whole screen over the desktop's own stream instead, and watches no frames (ADR 0058 §7).
- **Not done:** encoding video (H.264 over the same sockets, decoded with WebCodecs) would cut the bytes of scrolling and animations further, but needs an encoder on every computer and is not available in the phone app; it waits for measurements (`capturedAt`, the views' counters logged when each ends). WebRTC was ruled out: it needs a TURN server reachable over UDP, and a self-hosted install needs only Postgres. Distance to the server is the floor under all of it: every picture and every click goes through it.

### 8. What is stored

- Not stored: frames (the relay holds only the newest frame of a running stream, in memory; the first-frame screenshot is deleted on the computer once sent), screenshots (they stay in the agent's folder), the profile and cookies (on the computer), what a person types, the pages of a person's turn (in memory until the agent reads the page again).
- Stored: the run's transcript as for any tool (the `browser_*` calls and results), model usage and cost as for any model call, and one record per handoff or take over (who, when, result). No per-action audit table.
- After the run, the agent's message keeps where it browsed (`meta.browser.steps`: each `browser_*` call's tool, the site of an open without its query string, the time, whether it failed) for the card that stays in the chat. It shows a drawn page, never a picture of the real one.

### 9. Watching and stopping

- Live view on the run and on the machine page ("Dev is in the browser · shop.example/checkout"), with Watch and Stop.
- Always there, run or not (status, preview, take over; the card in the chat stays the default): a "Navegador" entry on the agent's page and its side panel, in the agent's DM header, and on the phone's agent profile, for the agent's owner and admins once it has `browser:use` and its computer serves the browser (the others who may watch, §6, get it where the request or the run is; the phone's profile also shows them a waiting request and a person's turn). It opens the same live view: Watch, Take over, Stop, and while in control an address field and Hand back with a note. The phone has no address field yet, so it offers Take over and Stop only while a page shows. The tray's Ver opens it too (`?browser=1` on the agent's web page).
- Stop closes the session at once.
- Try again, on a view whose page didn't come (`POST …/agents/{agentId}/browser/restart` → 204 once it closed, only who may drive it): the browser opens again in the background on the page it showed (else it starts blank, except during a person's turn, when it stays closed for them to open a site), its logins kept, and every view gets the stream again, also when the close or the open failed (meanwhile a view isn't told it's closed). The person in control pressing it keeps their control while it comes back. The view also watches again, as someone who only watches does: its own watch may be what was refused.
- Checkout only in test mode; a real payment or any sensitive action the agent recognizes becomes an approval card as usual. Page text never grants permissions or skips an approval.

### 10. Runner protocol 12

- `access.tools.browser`; `hello.browser { available, version, chrome, reason? }`.
- Ops: `browser.act { agentId, command, args }` (one `agent-browser` command, returns its JSON), `browser.stop { agentId }`, `browser.stream.start | stop { agentId, mode: watch | control }`, `browser.input { agentId, events[] }`; frames come back as `browser.frame` on the machine socket (`metadata: { deviceWidth, deviceHeight, pageScaleFactor?, url?, title? }`). A stream start on a closed browser fails with the error code `browser_closed` (older runners: `bad_request`).
- The server only offers the tools to agents whose machine reports protocol 12 with the browser on.
- Protocol 27 (2026-10-30): `browser.warm { agentId, desktop? }` → `{ started }` (§11); the answers of `browser.act`, `browser.batch` and `browser.warm` carry `setup`, what they waited on before running. The server sends `browser.warm` only to runners on 27 or later.

### 11. Ready before the first command (2026-10-30)

An agent's first use of its browser took about a minute, in the chat and on its computer's page. Measured in production on 2026-10-30, across agents: the first `browser_open` or `browser_do` 34 s on average (up to 56 s), the second 37 s (up to 69 s), the fourth about 8 s. ADR 0058 §14 measured 29 s for a first command in system mode. That first command paid everything at once: the agent's worker starting (system mode), `agent-browser` (about 20 MB) and Chrome for Testing (a zip of about 150 MB, about 380 MB unpacked) downloaded into each agent's own home through its own network counters, the agent's desktop starting, and Chrome starting.

- **Installed with the computer:** in system mode, once per computer at install time (§2), so no agent downloads anything at its browser's first use. A computer already serving a workspace gets it the next time its installer runs, without touching a running Chrome; the runner then restarts as for any new runner. Outside system mode (the desktop app, a person's own user), each install stays per user, but starts in the background as the runner starts with the browser on, or when the browser is turned on, instead of at the first command; a failure there leaves the next command to try again at once. The person's runners (one process per organization) take turns at it through `~/.agent-browser/install.lock` (taken over when its runner is gone), since all of them start together and `agent-browser install` writes one folder for the user.
- **Started ahead (`browser.warm`):** the server asks the runner to start the agent's Chrome when a run's judge lists the browser's tools (tools on demand, ADR 0043), while the model thinks, and when a person opens the agent's desktop (a desktop stream allowed, the agent not held) or its browser's live view. Only for an agent with `browser:use`, on the computer its next command would go to (a mission's in its thread), online, on protocol 27, serving the browser (its switch on), with nobody in control of that window or asked to take it; with `desktop` where its Chrome belongs on its desktop (§4), and only while the computer's desktop switch is on. The hub refuses it like any new work: a paused computer, a held agent or workspace. Nothing waits for it, and a refusal costs only the head start.
- **On the runner:** nothing starts (`started: false`) while a person has the agent's browser or is asked to take it, while its Chrome runs or starts (never moved: the next command moves it, under the rules of §4), or when opening its session would take the computer's last free browser. Otherwise it takes its place in the agent's queue like a command: Chrome on a blank page, headed on the agent's desktop or headless, no stream, no `agent-browser`; commands that come meanwhile wait behind it; the idle stop counts from it. In system mode root lends the agent's desktop to the worker only while that warm runs, as for a command. A person watching the agent's desktop sees its Chrome open there, blank.
- **Timed:** each answer says what its request waited on before it ran (`setup`, in ms, each only when it took 10 ms or more): `worker` (root, a worker started for it), `install` (getting the session ready: downloads, `agent-browser install`, or waiting on another request's), `queued` (requests ahead of it), `desktop` (the desktop started for it) and `launch` (Chrome started, moved, and its traffic counter attached). The runner's log line says it (`… 34123ms (install 28.1 s, desktop 2.3 s, launch 1.4 s)`), and the server sums it per tool call into the `tool_result` step (`data.timing.setup`, next to `ms` and `steps`).
- Left out, each until its reason shows: starting the `agent-browser` daemon in the warm (if the first command's own time still shows it); removing the per-agent Chromes agents installed before (the worker can do it as the agent); the bind policy a new agent's first worker checks twice; a warm at run start without a judge (servers without Jev).

### 12. A page that dies (2026-10-31)

A tab's renderer can die under the agent: Chrome then shows its sad tab ("Aw, Snap!", "error code 5": SIGTRAP, Chrome's own check when an allocation or a thread start fails), the agent's commands fail or time out, and people watching see Chrome's page with its Reload button. The agents reaching their shared memory limit (`agents.slice`, ADR 0057 §2) causes it.

- **Opened again, once:** the runner's own DevTools connection to each Chrome (the traffic counter's, protocol 23) hears it (`Inspector.targetCrashed` on the tab's session) and sends the tab to the address it was on: its history's current entry, through `Page.navigate`. Not `Page.reload`, which posts a form's answer again without asking (Chrome's own Reload asks): a page that answered a form is fetched again, never posted again. The live view and the agent's desktop show the page loading again.
- **Said to the agent's next action, instead of running:** the refs it read and the page it saw are gone, so its next action runs nothing and is answered with what happened ("The page ran out of memory and was reloaded, so this wasn't done. Read it again before you go on."), and the action the page died under is answered the same way ("The page ran out of memory while this ran, and was reloaded. …"). It ran out of memory when, since its Chrome started or a page last died, the kernel stopped one of the agent's processes for memory (`oom_kill` rose in its slice's `memory.events`) or an allocation failed at the limit all agents share (`oom` rose in `agents.slice`'s), otherwise the page "crashed". Not `agents.slice`'s `max`: with the agents' cache at their limit it rises at every allocation. Outside system mode the agent has no slice of its own, so it is "crashed".
- **Only an action is told:** a look, a wait and a command that tolerates failing run on the page as it is, since the server ignores what they fail with (a plan's look after an action, the pauses and looks of its waits and checks, the handoff's keepalive and the live view's `get url`), and an answer there would be lost. In a `browser.batch`, a page that dies after an action (under the settling after a click, say) is said by that action's answer, in place of its own and of what followed: a plan stops at that step, and its report says why. One that died before the batch is said by its first action, which doesn't run. While a person has the agent's browser or is asked to take it, nothing is told, so a person opening a site is never refused: the agent hears it at its first action after their turn.
- **Never a loop:** a tab that dies again before the agent heard of the first isn't reloaded: it shows our notice instead of Chrome's sad tab (a page of ours in the app's look, in pt-BR and English since the runner can't tell who watches: "A página ficou sem memória", "O agente será avisado"), once. A third death leaves Chrome's own page: a page that can't even start there (the agent's slice at its last task, or its memory held by a process that isn't Chrome) dies again at once, and each new page would start a renderer only to die. The agent hears "The page ran out of memory again, so it wasn't reloaded a second time. Open it again only if you need it." Once the agent heard, a page that dies is reloaded again.
- Left out: a frame or worker whose renderer dies (Chrome reports only the tab's page, and draws its own sad frame inside the page); a Chrome that dies whole (its next command starts it again, as before).

### 13. Logins: out of the agent's commands, kept across restarts (2026-10-31)

- **Out of its commands.** The profile sits in the agent's own folder, where its commands run, and Chrome on Linux keeps its cookies there under a key anyone can read (`--password-store=basic`), so a copied cookie file is a working login elsewhere. `.agentes/browser` is now one of the command policy's secret folders (`SECRET_DIRS`, `packages/adapters/src/command-policy.ts`): a command or read tool that names it is refused at once, by Claude Code's own rules too, and so is a path inside any agent's profile through the file tools (`read`, `push`, even through a symlink). A folder zipped for `push` goes without it, so the agent can still send its whole folder. The runner and the agent's Chrome keep using it. The rest of `.agentes` (a mission's files) stays the agent's to read. Like every secret folder, this is a check on what a command names, not a wall: a command that builds the path at run time, or one Codex runs without asking, isn't stopped; that waits for Chrome under its own user (protected mode, ADR 0030). The same ceiling holds for Chrome's DevTools port: Chrome listens on 127.0.0.1 (`--remote-debugging-port`), and in personal mode the agent's commands run as the same user, so a command can connect to it and read the profile's cookies (`Network.getAllCookies`) or a password field the browser just typed into, without naming the folder. Nothing refuses that until Chrome runs as its own user.
- **Kept across restarts.** The agent's Chrome stops after 15 idle minutes and restarts when it moves to or from the agent's desktop. A site that keeps you signed in only until the browser closes (no "remember me") lost its session at each restart: Chrome drops session cookies at the next start unless it restores the session. Measured 2026-10-31 on Chrome for Testing 155, headless: without `--restore-last-session` a session cookie was gone at the next start; with it, it stayed, and so did the last session's tabs. So Chrome starts with `--restore-last-session` and the runner removes `Default/Sessions` before each start: the cookies come back, the tabs don't, and the agent's browser starts on one page as before (the agent never finds old tabs, and nothing piles up across restarts).
- **Closed, then signaled.** The runner stopped Chrome with SIGTERM. Measured the same day: cookies set a second and a half before a SIGTERM were gone at the next start, the "remember me" one too in three runs of four; 35 s before it, or with `Browser.close`, they stayed. A sign-in just before the browser moved to the agent's desktop could be lost. The runner now asks Chrome to close itself through its own DevTools connection (the traffic counter's, protocol 23: `Browser.close`, about 0.1 s), and signals it only when it is still there after 2 s.

### 14. Dragging, not only clicking (2026-10-31)

A person in control couldn't solve a slider captcha ("slide right to secure your access"), in the chat's card or in the computer dialog: the view sent a click when the mouse's click came (the press and the release together, at the end), and the phone sent a tap. A press that moved never reached the page.

- **Mouse and pen** (the web and the desktop app): the left button goes down on the page when it goes down on the frame (the pointer moves there first), every move while it is held goes as a move with the left button, and it is let go where it is released. A click is the same with no move between. The frame captures the pointer, so a drag that leaves it stays at its edge and still lets go. Scrolling (a wheel or a trackpad) moves the page once the page was pressed, as before, and the hint over it says so in two short sentences that fit a 300 px page: "Rolar agora move a página. Esc para sair" (it said "Rolando a página", which read as if the drag had turned into scrolling).
- **Fingers** (the web on a touch screen and the phone app, one rule in `@agenteschat/client`, `createTouchInput`): while the person is in control, a tap clicks where the finger landed; a finger that moves more than 8 px of the frame drags, pressed where it landed and let go where it lifts; two fingers scroll the page with wheel events that follow them. The frame takes the touch at once (`touch-action: none` on the web; on the phone a manual gesture activated on touch-down, on the UI thread), so the conversation doesn't scroll under a drag; it still scrolls from anywhere else. While a finger moves, the hint says "Arraste com um dedo. Role com dois". A first finger on the band around the picture starts nothing.
- **Timing:** each mouse event says when the person made it (`at`, ms on the sender's clock). The runner plays a drag (from its press to its release) with the gaps the person made, each at most 100 ms: the server gathers input 25 ms at a time and a slow link bunches it, and a slider handed a whole drag at once jumps to its end. Clicks, hovering and senders without `at` go at once. The app sends a drag's moves every 25 ms (it was 16): the server gathers that long anyway, and a long drag stays well under its 60 input messages a second, past which a message is dropped, possibly the release. The sender writes `at`, so the gaps never put an event more than 1 s behind the time its batch reached the computer (`DRAG_LAG_MAX_MS`): 100 ms gaps alone let one batch of 100 events hold the input queue for 10 s, and a socket queue minutes of it.
- **When control ends:** the server checks control only as it forwards a batch, so the runner drops what is still queued (counted as failed) once the stream is back to watching or ended. A button still down then lets go where the pointer was (back to watching, or the stream stopped because nobody watches), after the queued input, so the agent doesn't go on with it held.
- A person's pointer input goes over the runner's own DevTools connection to the active tab's CDP session, fire-and-forget, so a busy renderer can't hold a click behind an unanswered command. Every event carries CDP's `buttons` mask, so a move after a press reaches Chrome with `buttons: 1` and the page sees a drag, also from an app that names no button on its moves. Keyboard and text keep the `agent-browser` command relay. The pin is `agent-browser` 0.39.4: its `page_wedged` recovery reports a tab that stopped answering and replaces it with a blank one after the second timeout, while a page that recovers keeps its tab.
- **A release that never came:** a press now goes apart from its release, and the release can be lost (a socket reconnecting, a batch the server refuses after control changed, the rate limit, a card that resets when control ends). The runner sends it first, where the pointer was, before a press of a button it still holds or a move that says no button is down, so the next click doesn't drag from the old press. A move that names no button still drags (older apps send it so).
- The computer dialog: in control of the browser it shows the same page card, so it drags as above. The agent's screen (noVNC, ADR 0058) already dragged: noVNC sends its pointer with the buttons held, a mouse at once and one finger once it moved 50 px, and two fingers scroll.
- No new protocol: `at` is an optional field that older runners and servers drop (their drags play at once). Double click and the right button stay as they were.

### 15. Paste, the address bar, and a request on the screen (2026-11-04)

A beta customer, the only owner of his agents, could not paste into a sign-in page the agent handed him, and neither could an admin on another person's agent. Both were in the page view (the hand-off opened it for anyone, even on a computer whose screen they may drive), and the page view had no working paste: the person's ⌘V/Ctrl+V went to the agent's Chrome as a key (`keyboardEvents`), which pasted the agent's own clipboard (empty), and with that key taken the browser never fired the paste event the card listened for. Its page also sat in a grey padded frame, with the address behind a globe button.

- **Paste:** the person's paste keys are the browser's own: the view sends no key and puts the focus, for that keystroke, in a text field nobody sees inside the page (only an editable element gets a paste in every browser, Safari and the Mac app included). Its paste event brings the person's text (`clipboardData`, no permission asked); it is typed into the page's focused field as text (`keyboard inserttext`, CDP `Input.insertText`), line breaks as LF, in pieces of at most 10,000 characters (one `text` event's limit), never splitting a character, and at most one piece a frame (`pasteEvents`; the server drops larger frames). The focus goes back to the page. A paste with no text, or over 256 KB (the screen's limit, ADR 0058), is said and nothing is sent. **Colar** at the address bar's end reads the clipboard where the person's browser allows it (it may ask); refused, it says to use ⌘V or Ctrl+V on the page. The phone's keys row has Colar too (its own clipboard, the same pieces); its text field still takes the phone's own paste.
- **Copy** out of the page isn't brought back yet: ⌘C/Ctrl+C copies on the agent's computer. Bringing it back needs the runner to read the page's selection; the whole screen (§16) already brings copies back (ADR 0058).
- **The address bar** is always at the page's top while the person is in control, as a browser's own: the page's address (no scheme at rest), selected whole on focus, Enter opens what is typed, Esc puts the address back; back, forward and reload before it. Watching in the computer dialog it shows the address alone, read only; the separate site line and the globe toggle are gone. The arrows go through the same route as an address: `POST …/browser/open` (and a profile's `…/open`) takes `{url}` or `{go: back | forward | reload}`, only for the person in control, as `agent-browser`'s own commands.
- **Edge to edge:** in the computer dialog the page has no ground or padding round it, as the screen has none: it fills the stage's width under the bar, keeping its shape.
- **A request on the screen (§16):** see ADR 0065 §1: a browser request whose window is on the agent's screen is helped on the whole screen by whoever may drive that screen.

### 16. A browser request on the agent's screen (2026-11-04)

Where the agent's Chrome runs on its desktop (ADR 0058 §7), the browser's open handoff also holds the screen. Someone who may drive the computer (`computerDriving`) and holds that handoff (a request they took, or a take over of the browser) now drives the whole screen: the desktop's control stream is allowed for them (`streamAccess`), their watching stream switches to control in place when they take it and back when they hand it back (`createDesktopControl`), and leaving keeps control for the grace as on the screen's own handoff. The apps open the computer dialog on the screen for them (`drivesOnDesktop`), with the request's banner on top and Pronto / Não consegui as before; the chat card's Abrir aqui opens that dialog instead of the page. Everyone else (who may drive only the browser) gets the page as before, and so does a computer without screens. Someone other than the owner who gets the screen this way is audited and the owner told, as for a take over of the screen (`desktop.control_taken`, ADR 0059 §8). The agent hears the same browser hand back (`done`, `failed`), and reads the page again.

## Consequences

- Agents browse on connected computers with any brain and any model, reading pages as text, and keep their logins per agent.
- A person helps from anywhere through one handoff: a card, a push, a live view, Done.
- No new infrastructure: one replica, frames in memory, nothing from the browser stored in Postgres.
- We depend on a third-party binary: pinned, hash-checked, behind our tools, replaceable by our own CDP code.
- A second native executable to sign and ship in the app, and a download path for terminal installs.
- One Chrome per active agent costs memory; the per-machine cap bounds it.
- Until protected mode, a login in an agent's profile is readable by other unprotected agents and the owner on that computer, hence the test-or-agent-accounts rule.
