# 0056. Operator API and external provisioning

- Status: Accepted (2026-10-24). Amended 2026-10-25 by ADR 0065 (§10: the ready time and when the wait began, the ready email, no pairing with external provisioning, no approval step), 2026-10-26 (§10: a workspace on hold or suspended waits for no computer), 2026-10-27 by ADR 0079 (§4: limits and meters; §5: `platform_ai.threshold`; §8: billing holds, limits and the create refusal) and ADR 0076 (§5, §6: screened sessions), 2026-10-29 by ADR 0078 (the sign-up mode, the waiting list and early-access invitations), 2026-10-30 by ADR 0082 (§5: `agent.deleted`) and ADR 0088 (§4: a workspace's deletion and deletion hold; §5: the deletion's events; §8: a deletion is no standing; §9: the deletion hold; §10: a workspace being deleted waits for no computer), and 2026-10-31 by ADR 0089 (§5: `run.hop_limit`) and ADR 0103 (§4: the analytics reads), and 2026-11-02 by ADR 0127 (§4: the work analytics reads), and 2026-11-05 by ADR 0150 (§4: the Claude sign-in policy and the AI-accounts reads; §5: `account.failure` and a failed `run.finished`'s `failure`), and 2026-11-09 by ADR 0161 (§5: `machine.wake_wanted`; §10: the workspace's computer in standby, `busy` and `lastUsedAt`), and 2026-11-13 (§2: a second, read-only token; §4: the lookups, runs and conversations, and jobs and usage; §10: what is on a computer; the addenda below)
- Date: 2026-10-24
- Extends: ADR 0002 (nothing private runs in the server process), ADR 0004 (configuration), ADR 0025 (connected computers)

## Context

Whoever runs an instance for other people (agentes.chat Cloud is one) needs things the app's own API doesn't give: look up any workspace or account to answer a support or abuse case, hold or suspend a workspace, and give each workspace a computer prepared by an external provisioner the operator runs. ADR 0002 rules out a private module inside the server process, so those services run apart and talk to the server over the network.

The app API (`/api/app/*`) is the wrong door for them: it acts as one person (cookie session, CSRF), it changes freely between versions, and it sits on the public address.

## Decision

### 1. Its own listener, off by default

- `OPERATOR_API_TOKEN` (at least 32 characters) turns it on. Unset, nothing listens. Set, a second `Bun.serve` on `OPERATOR_API_PORT` (default 3001, same `HOST`) serves `/api/operator/v1/*` and nothing else (`apps/server/src/operator/app.ts`, started in `start.ts`).
- The public listener (`PORT`) never mounts it: `/api/operator/*` there is a 404, token or not.
- The port belongs to the operator's private network. The compose file doesn't publish it; a service on the same Docker network calls `http://agentes:3001`. It is never published nor put behind the public reverse proxy.

### 2. One bearer token

- Every request carries `Authorization: Bearer <OPERATOR_API_TOKEN>`, compared in constant time. Anything else is a 401, on every path under the prefix (unknown ones and the OpenAPI document too), so nothing about the API answers without it.
- A second token that only reads may be set beside it (added 2026-11-13, the addendum below).
- No cookies and no CORS headers, so a web page can't call it on a visitor's behalf.
- The token reaches every workspace and account on the instance. It lives only in the server's environment and the caller's, is never logged (`secret: true` in the schema), and is rotated by hand.

### 3. A versioned contract

- The caller deploys apart from the server, so a server deploy must never break it silently. The version is in the path, `/api/operator/v1`.
- The OpenAPI document is served at `/api/operator/v1/openapi.json`, and a copy is committed in `apps/server/test/operator-openapi.json`. A test compares the two, so every change to the contract is a reviewed diff.
- Adding an endpoint or a field keeps `v1`. Renaming, removing or changing the meaning of one makes `v2`, served next to `v1` until the callers have moved.

The lookups that start from what a report quotes (an address, a handle, a link) and a workspace's members, channels and agents came 2026-11-13 (the addendum on lookups below), and with them what a run did and why a message started one or none (the addendum on runs and conversations), and the job queue and what model calls spent (the addendum on jobs, usage and computers).

The reads live in `packages/engine/src/operator.ts` and pick every field by name, the analytics reads in `packages/engine/src/connector-usage.ts` and `work-analytics.ts`, which give counts, keys and ids only. ### 5. The events feed: what happened, as metadata

`GET /events?after&limit` (up to 1000) answers `{ events: [{ id, at, type, orgId, userId, data }], next }`, oldest first. `userId` is the person the event is about or who acted. The server writes each event in the transaction of what it records (or right after a sign-in commits), in `operator_events` (`packages/engine/src/operator-events.ts`):

| Type | Written when | `data` |
| --- | --- | --- |
| `user.signed_up` | an account's first sign-in method is created | `email`, `method` (`email`, `google`, `github`, `apple`) |
| `session.created` | someone signs in | `ip`, `userAgent` (512 characters at most) |
| `user.deletion_requested` | a person deletes their account; `dueAt`: when it goes for good | `dueAt` |
| `user.deletion_canceled` | they restore it before that date | none |
| `user.deleted` | an account is deleted | none |
| `organization.created` | a workspace is created | `name`, `mode` (`team` or `personal`, ADR 0159) |
| `organization.deletion_requested` | an owner deletes a workspace, or its only member deletes their account, and it is read-only for 7 days (ADR 0088); `userId` is who asked | `dueAt`, `via` (`owner` or `account`) |
| `organization.deletion_canceled` | an owner restores a workspace being deleted; `userId` is that owner; `via: "account"` when it came back with its member's account | `via` when so |
| `organization.deleted` | a workspace's data is deleted, at the end of its deletion's 7 days (ADR 0088); `userId` is who asked, null once their account is gone | `requestedAt`, `via` |
| `invitation.created` | an invitation is sent or resent, or an invite link is made | `emailDomain`, `role`, `resent: true` when resent; `link: true` for a link |
| `agent.created` | an agent is created | `agentId` |
| `agent.deleted` | an agent is deleted for good (ADR 0082) | `agentId` |
| `mail.sent` | an agent sends, replies to or forwards an email | `agentId`, `runId`, `kind`, `recipients` (how many), `domains` |
| `run.finished` | an agent's run ends (done, failed or canceled) | `runId`, `agentId`, `brain`, `status`, `toolCalls`; a failed one `failure` (`code`, `cause`, ADR 0150 §5) |
| `account.failure` | a turn on a computer's AI account fails for a provider's or sign-in reason, at most once per account and cause every 10 minutes (ADR 0150 §5) | `accountId`, `machineId`, `kind`, `authMethod`, `cause`, `code`, `httpStatus`, `runnerVersion`, `protocol` |
| `machine.wake_wanted` | something wants the workspace's computer while it is in standby: a run (`run`), a person opening its view (`view`) or a request to it (`call`), at most once per computer every 10 seconds (ADR 0161) | `machineId`, `why` |
| `run.hop_limit` | the depth backstop (`AGENT_MAX_HOPS`) stopped an agent's hand-off: the per-stretch limits stop agents long before, so some path lost its stretch (ADR 0089) | `messageId`, `hop` |
| `task.finished` | a task on a computer ends (done, failed, canceled, or interrupted for good) | `taskId`, `agentId`, `executor`, `status` |
| `desktop_control.ended` | a screened segment of a person's control of an agent's screen ends, having read something (ADR 0076; only with `SESSION_SCREENING`); `userId` is who was in control | `agentId`, `segmentId`, `startedAt`, `endedAt`, `screens` (how many) |
| `content.viewed` | a review block is read (§6) | `ref` (`run:<id>`, `task:<id>` or `session:<id>`), `reason`, `operator` |
| `platform_ai.threshold` | a workspace's usage billed to the platform this UTC month first reaches 50%, and first reaches 100%, of its `platformUsdPerMonth` limit (ADR 0079) | `month`, `percent` (50 or 100), `spentUsd`, `limitUsd` |

- **Metadata only.** Ids, counts, domains and where a sign-in came from: never a message, prompt, subject, address list, file, credential or token. Content leaves only through §6.
- **Off by default.** Events are recorded only while the operator API is on (`OPERATOR_API_TOKEN` set); without it the table stays empty. `content.viewed` is always recorded, since a review block can't be read without the API.
- **No foreign keys.** An event outlives the workspace or account it names: that is when an abuse case needs it.
- **Paging never skips an event.** Ids and timestamps are taken before a transaction commits, so a slow transaction can commit an event that sorts before one already served. Each row keeps the id of the transaction that wrote it (`xid8`, from `pg_current_xact_id()`); the feed is ordered by it and serves only rows whose transaction is below `pg_snapshot_xmin(pg_current_snapshot())`, the point below which every transaction has ended. A row committed later always sorts after the cursor. The cost: a long transaction anywhere on the database holds the feed back until it ends; nothing is lost meanwhile.
- **`next`** is opaque. Pass it as `after`; an empty page returns the same value, so the caller polls with it until something new comes. Callers skip types they don't know: new types and fields keep `v1`.
- **After a restore from a dump.** `pg_dump`/`pg_restore` brings the rows but not the transaction counter, so the restored database numbers its transactions anew, below the restored rows. A cursor from before the restore is then past every id the database gave out: it is refused (400 `stale_cursor`) instead of waiting forever, and the caller starts again without `after`, skipping the event ids it has (they never change). The restored rows themselves would stay behind the commit horizon until the counter got there, so the server moves them to the front of the feed when it starts, before the operator API serves a page.
- **Kept 90 days** (pruned daily by the workers). The operator's services copy what they need and keep it under their own retention rules.

### 6. Review blocks: the only content

`GET /review/{run|task|session}/{id}?reason&operator` answers `{ kind, id, orgId, agentId, text }`: what one run or task did, or what was on an agent's screen while a person controlled it (a session, ADR 0076), for an abuse review (`packages/engine/src/operator-review.ts`).

- **Built by the server, never raw rows.** A run's block holds the message that started it, each tool call with its input and result, and the reply; a task's holds its title, the message behind it, its prompt, command, result, last lines of output and the files it touched; a session's, one screened segment of a person's control, holds the text of its first and latest screens, from the server's memory only, gone 10 minutes after the segment ends (a 404 then, and always on a server without `SESSION_SCREENING`). Plus a header of ids, brain or executor (or who was in control), status and times.
- **At most 12,000 bytes.** Every piece is cut first; when they still don't fit, the lowest-ranked go (tool calls before the request and the reply), and a last line says how many were left out.
- **Credentials masked** by their shapes (API keys, tokens, `Bearer` headers, `password=` and `token:` values, private keys) before anything is cut. Tool inputs are written as `key: value` lines so a field named like a secret is masked too.
- **Workspace text is quoted.** Everything people, agents, tools or web pages wrote is inside `<external_data>` envelopes, with any copy of the markers neutralised, so the reader (a person, or a model that judges it) weighs it as data and never follows it.
- **Every read leaves a trail.** `reason` and `operator` are required; a `content.viewed` event is written before the block is returned, in this server's database, where the operator's own services can't erase it.

### 7. Hooks are pulled, never pushed

The server never calls the operator's services. What it has for them waits in Postgres until they ask (the events feed above), and what they decide comes back through this API:

- standing: a workspace `active`, on `hold` or `suspended` (§8), an agent held, an account blocked; set here and enforced by the server at its existing choke points (model gateway, computer calls, permission checks, invitations, sign-in);
- external provisioning (`MACHINE_PROVISIONING=external`, §10): each workspace without a ready computer is a request the provisioner lists. It reports progress, and asks for a single-use enrollment code that the computer redeems through the device-code flow of ADR 0025, so the computer's own token never passes through the provisioner.

Nothing is lost while those services are down, and the server needs no delivery, retry or signing code. These endpoints join this API under the same token and the same contract test.

### 8. Workspace standing

`PUT /orgs/{orgId}/standing` with `{ state: active | hold | suspended, reason (64 characters at most), note? (2000), notice: shown | silent }` answers `{ state, reason, note, notice, changedAt }`. It is enforced where work starts, in `packages/engine/src/standing.ts`, never by a caller remembering to check:

- **`hold`: the agents stop.** The Model Gateway refuses every call. The machine hub refuses new work, and the bridge calls (`mcp.call`, `mcp.list`) of work already on a computer. A run that starts fails at once and says so, before any judge or model call, and leaves no new run for the messages it had taken. A routine's slot is skipped (`org_paused`) and the routine keeps its schedule. The router and the judge ask nothing: Jev bills the server, not the workspace. No invitation is sent, resent or accepted. People still read and write.
- **`suspended`: the workspace is closed.** All of the above, and every permission check (`requirePermission`, channel access) refuses with `org.suspended` (403). What its agents still have going stops each time it is set to `suspended` (so setting it again finishes a stop that failed halfway): every run not finished is canceled with the standing's text (a routine's run ends `org_suspended`) and hands its unread messages to no new run, and every live task is canceled on its computer (`task.cancel`; one the computer doesn't run, or that doesn't answer within 15 seconds, ends here and never resumes).
- Someone in a workspace that is suspended or on a hold, or whose account is blocked, can't create another one (`org.create_refused`), so the work doesn't carry on elsewhere. A billing hold (ADR 0079) refuses nobody, except the owner of a workspace waiting for its first plan (`payment`): `org.create_unpaid`, with that workspace's id.
- **Billing holds and limits** (ADR 0079). `PUT /orgs/{orgId}/billing-hold` with `{ hold: payment | unpaid | ended | null }` answers `{ applied, standing }`: a shown hold whose reason is that code, written like any standing here, and never over a hold set through `PUT …/standing` or a suspension (`applied: false`, as when it is already so). `PUT /orgs/{orgId}/limits` with `{ members, membersMax, payerUserId, storageBytes, uploadBytesPerDay, platformUsdPerMonth }`, each null for no limit (`membersMax`, the plan's top with seats added, and `payerUserId`, who pays for the plan, may be left out), answers them with `updatedAt`, which moves only when a value changes; limits and standing are independent.
- **A deletion is no standing** (ADR 0088, added 2026-10-30). A workspace an owner deleted is closed to changes and to all work (`org.deleting`, 403) for 7 days, its members still reading it (amended 2026-11-11), in columns of its own: setting a standing neither reads nor clears it, `standing` here, in `GET /me` and in `org.standing` never carries it, and `GET /orgs?standing=` filters by the standing alone. Past its date, a suspension or a hold that isn't billing's makes the deletion wait until it is lifted; a billing hold doesn't.
- **`shown`**: the workspace reads the reason ("This workspace is on hold: …", error `params.reason`), the change goes into its audit log (actor `system`), and a new state notifies its owners and admins (`org_standing`). **`silent`**: it reads only "Agents in this workspace are paused for review." or "This workspace is unavailable for now.", and gets no reason, audit row or notification: someone abusing it learns nothing about what was seen. Silent is only for when an authority's order forbids telling them. The note never leaves this API.
- Members hear `org.standing` (`state`, and `reason` when shown) on the workspace's realtime topic. Setting what is already set tells nobody again.
- Members also read it in `GET /api/app/me` (`organizations[].standing: { state, reason }`, the reason only when shown, never the note), so the apps know it before any refusal. On hold, the web app puts a line on top of the work area (the reason told, or only "Agents in this workspace are paused for review"); a run refused by the standing says so in the person's language (`run.org_paused` and its `reason`), not in the server's words. Suspended, the web and phone apps show a screen of their own instead of the workspace (why, when told; the person's other workspaces; sign out), with the socket still open so lifting it brings the workspace back at once. Both say where to ask about it: "Need help? Write to …" with the server's `SUPPORT_EMAIL`, else to ask the people who run the server.
- On agentes.chat Cloud (`isAgentesCloud(PUBLIC_URL)`) the standing in `GET /me`, `org.standing`, the refusals' `params` (`org.create_refused` too), a refused run's values and the owners' `org_standing` notice (`latest.cloud`) add `cloud: true`, and the apps follow a shown reason with how to contest it (legal@agentes.chat), in the inbox too. A shown standing whose reason is `review` reads as the automatic review hold's line, and `ended` (the hold of a workspace whose plan ended, a billing matter) reads as it is, with nothing to contest. A hold whose reason is `review.<category>` (`phishing_impersonation`, `account_takeover`, `fraud` or `illegal_content`) reads as the review line naming what was flagged, and a category the apps don't know as plain `review`. The standing's text (an error's message, a refused run's error) says a known category in words, never the code, and a run's values give the code back. The lines cite the Terms section they rest on by its number, and a test checks that number against the Terms this server serves. A self-hosted server's people read what they always read.
- Each process caches a workspace's standing for 5 seconds: a change applies at once in the process that made it and within 5 seconds in the others.
- What it doesn't stop: on `hold`, work already running on a computer (a background task, a computer brain's turn) goes on until its next model, computer or bridge call. The server never reaches a computer's network: cutting it off (on hold or suspended) is up to the operator's own controls on the computer, which the operator's service sets next to this call.

### 9. Agent hold, account block and deletion hold

- **`PUT /orgs/{orgId}/agents/{agentId}/hold`** with `{ held, reason? }` answers `{ held, heldAt, reason }` (`agents.operator_hold_at`, `operator_hold_reason`). A held agent gets the refusals of `hold` for itself only, with `agent.paused` (403): no model call, no new computer work or bridge call, a run of it fails at once ("This agent is paused for now.", `run.agent_paused`), its routines skip their slots (`agent_paused`), and the router never picks it, so the workspace's other agents answer instead. The workspace never reads the reason. Cached like the standing (5 seconds).
- **`PUT /users/{userId}/block`** with `{ blocked, reason? }` answers `{ blocked, blockedAt, reason, sessionsRevoked }` (`users.blocked_at`, `blocked_reason`, which Better Auth never reads, so they never reach a session or its cookie cache). Blocking deletes the account's sessions and phones (push devices), and Better Auth's `session.create.before` refuses it a new one (`ACCOUNT_BLOCKED`, 403, for every sign-in method). A signed session cookie keeps a browser signed in for up to 5 minutes without reading the sessions table, so the block doesn't wait for it: `getMembership` and `requireChannelAccess` read a blocked account as no member, so every permission check, channel and socket subscription refuses it on its next request, and its open sockets close at once (`membership.revoked` for each of its workspaces). It can't create a workspace, accept an invitation or delete the account (the workspaces where it is alone would go with it). Its memberships stay, so admins can still remove it or change its role, and unblocking gives everything back.
- `GET /users/{userId}` shows `blockedAt` and `blockedReason`.
- On agentes.chat Cloud the person reads the hold's or block's kind, never its reason, with how to contest it. A held agent's refusal and its runs' errors carry `{ kind, cloud: true }` (`network` when the reason starts with `network.`, else `operator`), and so does a blocked account's `ACCOUNT_BLOCKED` (`abuse` for `abuse.resignup`, `legal` for `legal_hold`, else `other`). Holding an agent there also notifies its responsible person and the workspace's owners and admins (`org_standing` with `latest: { statusTo: "agent_hold", holdKind }` and `source.agentId`). Held again for another kind, that notice closes and a new one says the kind its refusals now say. Letting it go closes it. No email is sent.
- **`PUT /orgs/{orgId}/deletion-hold`** with `{ held, reason? }` answers `{ held, heldAt, reason }` (`organizations.deletion_hold_at`, `deletion_hold_reason`), or 404 when there is no such workspace (ADR 0088, added 2026-10-30). It goes with a legal hold: while held, a workspace whose deletion was asked for, by an owner or with its only member's account, waits past its date instead of being deleted, closed, with everything in it. It refuses nothing and tells the workspace nothing (no audit row, no notice), restoring the workspace never lifts it, and once it is let go a deletion past its date goes ahead within an hour. `GET /orgs/{orgId}` shows it.

### 10. External provisioning: the workspace's own computer

`MACHINE_PROVISIONING=external` gives every workspace a computer from a provisioner the operator runs (`packages/engine/src/machine-provisioning.ts`, `apps/server/src/operator/machines.ts`). It needs `OPERATOR_API_TOKEN`: the server refuses to start without it, since nothing else would ever serve the requests. `off` (the default) changes nothing.

| Method, path | Answer |
| --- | --- |
| `GET /machine-requests?limit&cursor` | `{ requests: [{ orgId, orgName, createdAt, owner: { userId, email } \| null, provisioning }], next }`: every active workspace not being deleted whose computer isn't ready, oldest first, in keyset pages of up to 200. `owner` is its first owner; `provisioning` what the provisioner last said (null before anything). Empty with `off` |
| `PUT /orgs/{orgId}/provisioning` | `{ state: preparing \| waiting \| problem, step?, stage?, reason?, expectedReadyAt?, specs? }` → 204; 409 `provisioning.ready` once the computer is ready; 403 `org.paused` / `org.suspended` / `org.deleting` unless the workspace is active and not being deleted. An older client's `etaSeconds` reads as that many seconds from now |
| `POST /orgs/{orgId}/machines` | `{ name? }` → `{ machineId, enrollCode, expiresAt }`; 403 `org.paused` / `org.suspended` / `org.deleting` unless the workspace is active and not being deleted |
| `GET /orgs/{orgId}/machines` | `{ machines: [{ id, kind, managed, name, online, lastSeenAt, runnerVersion, protocol, standby, busy, lastUsedAt }] }`: every computer still in the workspace; `standby`, `busy` and `lastUsedAt` are the workspace's own computer's (ADR 0161), false, false and null for the others. Since 2026-11-13 each also says what is on it, and the answer carries `provisioning` (the addendum on jobs, usage and computers) |
| `PUT /orgs/{orgId}/machines/{machineId}/standby` | `{ standby }` → `{ standby }`: the workspace's computer is asleep by the operator's doing, or no longer (ADR 0161); 404 when the workspace has no such managed computer |
| `DELETE /orgs/{orgId}/machines/{machineId}` | 204; 404 when the workspace has no such managed computer (also once removed) |

- **A request is a workspace, not a row.** Nothing is queued: an active workspace whose computer isn't `ready` is listed until it is. One on hold or suspended is never listed, so a workspace whose computer was retired for abuse doesn't get another one; holding it is the provisioner's way to stop. Such a workspace waits for no computer (added 2026-10-26: the rows stayed, so a workspace ended before it got one read "waiting" for good): setting it on hold or suspended drops what the provisioner last said of its computer, in the transaction that sets it, every time it is set; a ready computer stays ready. A report reads the standing under a share lock on the workspace's row, which setting it waits for, so a report sent as it is held is either refused or dropped, never left behind; removing its computer reads it the same way and starts no wait. Its people are told of no wait: while it isn't active and its computer isn't ready, `computer-setup` and `machine.provisioning` say `state: null` and nothing of a wait (no step, time or size), and the apps ask for it again on `org.standing`. Active again, it is a request like any other. A workspace being deleted (ADR 0088) is no request either (added 2026-10-30): deleting it drops a wait that isn't ready, reports and codes for it are refused (`org.deleting`), removing its computer starts no wait, its people are told of none, and no ready email goes out. Restored, it is a request again. The provisioner reads its deletion in the events feed (§5).
- **One managed computer per workspace.** `machines.kind` is `connected` (a person paired it), `host` (the server's own) or `managed`. A unique index on `org_id` where `kind = 'managed'` (removed rows included) keeps one row: the first `POST` makes it (paired by nobody, no token yet), every later one reuses it, and one removed comes back. Unless `name` is given, it is named the way the apps call it, "Acme's computer" ("Computador da Acme"), in its first owner's language: a name like any computer's, so every message that names it says a computer, never the bare workspace. Renaming the workspace renames it too while it still has that name; a name someone gave it stays.
- **The code.** Each `POST` writes a confirmed `machine_device_codes` row for that computer (single use, 10 minutes, stored as SHA-256) and returns it once as `enrollCode`; an earlier code for it still unused is denied, so at most one works. The computer redeems it at `POST /api/machines/device/token`, the same poll as a code a person confirmed; the `machine.paired` audit row has actor `system`. The code names the computer as its own `previous_machine_id`, the reconnect case of the device-code flow, so one that expires unused never removes the row. A person's computer can never come back as the managed one through a reconnect code.
- **The computer's side.** `agentes-runner pair --server <url> --enroll-file <file>` (or the installer's `--enroll-file`, which connects even a home connected before) reads the code from a file, removes the file at once, whatever happens next, and polls with the code; nobody confirms anything. The code never goes on a command line, which other local users can read, nor into the runner's config or output. A file that doesn't hold something shaped like a code is refused before anything is sent. The config is written as for any pairing, in whatever home the runner uses.
- **Progress.** `preparing` (`step`: `reserving`, `starting`, `installing`, `connecting`), `waiting` (`reason`: `capacity`; an older client's `approval` reads as capacity, as do rows it wrote) and `problem` are the provisioner's; `ready` is the server's (`machine_provisioning.state`). `step`, `stage` and `expectedReadyAt` are kept only with `preparing`, `reason` only with `waiting`; `stage` is what the computer is doing within its step (`ordering`, `wiping`, `starting`, `booting`, `updating`, `restarting`, `network`, `firewall`, `apps`, `connecting`), any word of up to 64 characters being kept, so the provisioner can add one before the apps have words for it (they say its step meanwhile); `specs` (`{ cpus, memoryGb, diskGb }`) stay until replaced; `since` restarts only when the state, step or reason change. One wait (`preparing`, until ready, another state, a removal or a hold) counts down to the earliest ready time it was told: a later one is kept out, and a report without one keeps it, so a part running past its time, whose ready time moves later with the clock, reads as running over, never as a countdown that comes back up (ADR 0065 §3). Members hear `machine.provisioning` (the fields of `computer-setup` but `mode`) when something they see changes. Once `ready`, `PUT` is refused until the computer is removed, so a late write can't take a working computer back to "preparing".
- **When the wait began.** `requested_at` is written only when the computer is taken away and kept by every later report; null reads as the workspace's creation, so making a workspace writes nothing. A report that leaves the wait's ready time over a minute ahead, `waiting` or `problem` sets `email_when_ready`: the owners were told they'd get an email.
- **Ready on the first hello.** The managed computer's first hello since it was issued sets `ready` (a conditional write: only the transition counts), gives the computer to every agent of the workspace that has none, tells the members (`machine.provisioning`, `agent.computer`) and notifies the owners (`computer_ready`, in the app and on their phones). After a long wait (`email_when_ready`, or more than a minute since `requested_at`) a server that sends email emails them too, once, in their language, with the next steps, queued in the same transaction as the ready and only while the workspace is active (ADR 0065 §4). A reconnect changes nothing, so an agent someone moved off it stays where they put it. Agents created later start on the workspace's managed computer (or the server's own) once it has connected; the agent owner may put their agent back on it, though nobody paired it.
- **Removal.** `DELETE`, before the provisioner wipes or retires the computer, does what removing any computer does (its token stops working, its connection closes, its agents are left with no computer) and also denies its unused codes and starts the wait over (a `preparing` row with `requested_at` now), so an active workspace is a request again; one held or suspended is left with no wait. People can't remove the managed computer (`machine.managed`, 403) nor turn its tools off or take a folder away (`machine.managed_access`, 403): only the computer itself could undo that, and nobody in the workspace reaches it. Admins may still rename it.
- **What people see.** `GET /api/app/organizations/{orgId}/computer-setup` (every member) answers `{ mode: external | pair, state, step, stage, reason, since, requestedAt, expectedReadyAt, secondsLeft, secondsWaited, specs, notifyByEmail, machineId }` (all null but `mode`, and `notifyByEmail` false, with `pair`; `preparing` with nothing reported yet; `state` null and nothing of a wait while the workspace isn't active and its computer isn't ready). `secondsLeft` and `secondsWaited` (since `requestedAt`) are counted by the server when it answers; `notifyByEmail` says the server sends email. The computers list shows the managed one with `kind: managed` and no hostname, OS, arch or workspace folder; the offline computers and their targets (`…/machines/outages`) mark it `managed: true`, its platform `other`. An agent with no computer while its workspace's is still being prepared is told that (`computer_status`, its tools' descriptions) instead of "no computer".
- **The apps** (`setupView` in `packages/client/src/lib/computer.ts`, live from `machine.provisioning`) say where it is in plain words: the step ("Turning it on", 2 of 4), or the stage within it when they have words for it ("Updating the system", still 3 of 4), waiting (in line: no computer on its way yet), a problem, ready, or paused (`state: null`: on hold, nothing on its way, no notice, and the pickers offer it no more than when it is ready). Never a system, an address, a provider or a tool list: its size ("4 CPUs · 8 GB of memory · 100 GB of disk") and one user per agent are what it is. Until it is ready: a notice on top of the work area naming the agents that wait for it; the onboarding's computer step shows its progress instead of a choice, and the person goes on; Settings → Computers shows its card in place of the cloud computer's; an agent with no computer reads as waiting for it, and pickers offer it in place of "no computer", as the computer it will be (moving an agent there keeps its brain). Once ready, its card shows online or not and its agents, and on a server without the cloud computer the pickers no longer offer the cloud: an agent with no computer reads "No computer". Its page never offers Remove, the folder it was connected from or turning anything off; when its browser or the agents' desktops don't work, it says so and where to ask, never a runner's reason or command. It is drawn as a server before and after it exists, never as the cloud computer an agent may get of its own.

## Consequences

- A self-hosted instance gets no new surface unless its admin sets the token; with it, the same API serves their own automation.
- One token holds every operator power. Splitting it (read-only, per caller) waits for a second caller. (The read-only split came 2026-11-13, the addendum below; a token per caller still waits.)
- Answers carry personal data (names, emails, IP addresses), and with the token set the server keeps 90 days of events about people who may have deleted their account since. Callers keep what they copy under their own retention rules.
- The feed can lag behind by as long as the longest transaction running on the database.
- A change to the contract fails the test until the committed document is regenerated (`UPDATE_OPERATOR_OPENAPI=1` on `apps/server/test/operator.test.ts`), so it is always a deliberate diff.
- With external provisioning a workspace waits for its computer as long as the provisioner takes: nothing in the server times out or falls back to pairing, and its people can't connect computers of their own (`machine.pairing_off`, ADR 0065 §5); the server refuses to start with `HOST_COMPUTER_TOKEN` too.

## Addendum (2026-11-13): a read-only token

The second caller came: tooling that only looks things up, to answer a report or fill a dashboard, has no reason to hold the token that suspends workspaces, blocks accounts and opens review blocks.

- **`OPERATOR_API_READ_TOKEN`** (optional, at least 32 characters, `secret: true`) is a second bearer token on the same listener. The listener still exists only with `OPERATOR_API_TOKEN`: the server refuses to start with the read token alone, which would open nothing, and with the two equal, since the token that should only read would then hold every power.
- **What it may do.** `GET` and `HEAD`, and nothing under `/review/`: a review block is content, and reading one writes an event (§6). Anything else answers 403 `forbidden`, known route or not. No token or a wrong one is still 401 `unauthorized` on every path, and a server that didn't set the read token answers it 401 like any wrong one. Both are compared in constant time.
- **Decided in one place.** The middleware every request passes (`apps/server/src/operator/app.ts`) decides by method and path, never route by route. So a `GET` added to this API is readable with the read token from the day it ships: outside `/review/`, a `GET` never changes anything and never returns content.
- **Narrower, not harmless.** It reads everything §4, §5 and §10 answer to a `GET`: names, emails and IP addresses of every workspace and account on the instance. It is kept and rotated like the other token.
- A token per caller still waits for the need.

## Addendum (2026-11-13): lookups

A report rarely arrives with an id: it quotes an address, an agent's handle, a channel, a link. The reads of §4 start from a workspace's id and stop at its counts, so "who is this, and which agent do they mean" took a database shell. These reads answer it. All are `GET`, additive in `v1`, and open to the read-only token.

| Method, path | Answer |
| --- | --- |
| `GET /users?email&q&limit&cursor` | Accounts by their whole address (`email`) or by part of an address or of a name (`q`, any case, matched literally), newest first, in keyset pages of up to 200: `id, email, name, emailVerified, createdAt, blockedAt, blockedReason`, `deletionDueAt` when the person deleted it, `lastSignInAt` (its newest session on record), its first 20 workspaces with the role in each, and `orgCount`. One of `email` and `q` is required |
| `GET /resolve?ref&orgId` | What a reference names and where it lives: `{ form, matches }`, at most 20, each `kind, id, orgId` with the names and ids that kind has (`name, handle, email, channelId, threadRootId, agentId, runId, number, version, createdAt`). `ref` is a message's or a file's link (a path, or an address on any host), `@handle` (an agent's, one it had before too, or a member's), `#channel`, a task's number, an id, the first 8 characters of an id, or an account's id. What these keep, and every read added after them:

- **Who and what, never what anyone wrote (§4).** Names, handles, addresses and ids tell things apart; nothing else comes out. No message, no task's or file's title, no agent's instructions, no routine's prompt, no skill's or memory's text, no channel's topic, no invitation's or join request's note, no reason given for a refusal: of skills, routines and memories only how many. A direct conversation's and a task's conversation's stored names are made up, and `/resolve` leaves them out.
- **Never a secret.** No invitation link or its hash, no join request's claim or password hash, no session, no credential, key hint or wrapped key, no AI account's email. A test seeds each of these and fails if one shows up in an answer, or if any field is named like one (`apps/server/test/operator-lookups.test.ts`, as `operator.test.ts` does for the reads of §4).
- **Nothing is written.** The read-only token reaches them all, so none may change a row. The members' read is its own query for that reason: the app's list gives a handle to a member who has none yet.
- **Every list ends.** `limit` is 50 unless said, 200 at most, with a keyset `cursor`; a list inside an answer has a fixed size the document states. An account in every workspace of the instance still lists 20.
- **Ids are whole.** The start of an id is taken by `/resolve` alone and only inside one workspace, where it may name several things; every other read takes the id it answers.
- **A message by its id is looked up without a time range.** `messages` is partitioned by month (ADR 0009) and a message's id usually says when it was written, but a message can be placed at another time than its id says (`NewMessage.createdAt`), so `/resolve` asks every partition's primary key instead of guessing the month.

The reads are in `packages/engine/src/operator-lookups.ts`, the routes in `apps/server/src/operator/lookups.ts`.

## Addendum (2026-11-13): runs and conversations

"The agent didn't answer" and "why did it do that" are the reports an operator gets most, and both were answered with a database shell: the run's row, its steps, the routing decision and the jobs are all stored, in five tables. These reads put them together. All are `GET`, additive in `v1`, open to the read-only token, and keep every rule of the lookups above.

| Method, path | Answer |
| --- | --- |
| `GET /orgs/{orgId}/runs?agentId&channelId&threadRootId&status&errorCode&from&to&limit&cursor` | The workspace's runs, newest first, in keyset pages of up to 200. Each: its ids (`agentId, channelId, threadRootId, triggerMessageId, replyMessageId`), `trigger`, `hop`, `background`, `brain`, the `model` of its latest turn, `turns`, `status` as stored and `shown` as people read it, what it waits for (`waitCode, waitSource, waitResetsAt, waitingMachineId`), its `errorCode` and the first 500 characters of its `error`, and `createdAt, startedAt, finishedAt, heartbeatAt`. With `groupBy=error`: `{ from, to, errors: [{ errorCode, runs, firstAt, lastAt }], more }` instead, over the last 7 days unless `from` says |
| `GET /runs/{runId}/trace?limit&beforeSeq` | One run: its row as above; its `steps` in order, the last 200 unless paged back with `beforeSeq` (`seq, kind, at`, a tool call's `tool` and `connector`, a result's `isError`, `refusal` and `code`, an error's `reason` and `code`, a model call's `model` and `stopReason`, `chars` for how long a tool's input or result is, `durationMs` from a call to its result, a `message` step's `messageId`, and `records`, the names of what a `context` step noted); `stepCount`; `asks`, its approvals, questions and requests for a secret (`kind, id, tool, status, createdAt, expiresAt, resolvedAt, byUserId`); its `jobs`, newest first, at most 100 (`kind, status, attempts, maxAttempts, nextAttemptAt, lockedUntil, lockedBy, lastError` cut to 300, and `cause`, why that job woke the run); `usage` in all and `byModel` (`calls, input, output, cacheRead, cacheWrite, costUsd`); and the `machine` it is tied to |
| `GET /orgs/{orgId}/timeline?channelId\|messageId&from&to&limit&cursor` | One conversation's events, oldest first, in keyset pages of up to 200, each with its `type` and `at`: a `message` (`id, threadRootId, authorType, authorUserId, authorAgentId, runId, hop, length, mentionedAgentIds, mentionedUserIds, flags, edited, deleted`), a `routing` decision (`messageId, strategy, candidates` with their scores, `needsAgentScore, selectedAgentIds, reasonCodes, error`), a `run` when it began (the row above) and an `ask` when it was asked. The window is the 6 hours up to now, or the 3 hours before and after `messageId`; `from` and `to` move it, 48 hours apart at most |
| `GET /messages/{messageId}/explain` | Why a message did or did not start a run: a `verdict` (`run`, `joined`, `answered_question`, `mission_suggestion`, `kept_on_hold`, `no_ai`, `platform_cap`, `blocked`, `referenced_only`, `nobody_picked`, `picked_not_started`, `job_pending`, `job_failed`, `not_routed`), with `skipped` saying why nothing was decided; the message's facts as in the timeline; the `handles` its text names; up to 50 `agents` (the ones it names, mentions or was routed among, then the conversation's others), each with what the routing decision made of it, its `outcome`, the `run` that answers the message for it, and its state `now`; the `routing` decision; the `workspace`'s standing; and the job that routes it (`postedJob`) |

What these add to the rules above:

- **A step is what it did, never what it carried.** A tool call's input, a tool's result, a model's narration, the prompt and the transcript never leave. Sizes are measured in the database, so the text isn't even read out. A context step answers with the names of what it noted, not the notes.
- **A JSON column gives up named scalar facts only.** Steps, a run's transcript, a message's `meta` and a routing decision's candidates are read field by field, each fact only from the kind of row that writes it, and a value comes out only when it is shaped like what the code writes there (a code, an id, a time). A model's words stored where a code usually is read as absent. A job's `payload` is never read into an answer, and a run's jobs are found by their name, which outlives the payload.
- **A routing decision's `reason` is the router's own marks, not a step's words.** The stored text starts with marks written by code (`follow-up`, `default`, `for people`…) and goes on with what a model said about the message. Only the leading marks are returned.
- **Error text is cut, not hidden.** A run's error (500 characters), a job's last error and a routing decision's failed steps (300) are what providers, CLIs and our own code said went wrong, with anything shaped like a credential masked on the way out. The `errorCode` beside a run's error is the app's own (`runErrorDetail`), so counts and filters by code read the same as the apps do.
- **`@handles` that name nobody are counted, not listed.** An explanation reads the handles written in the message to say whom it names; a word after `@` that is nobody's handle is part of the message, so only how many there are comes out.
- **A cause comes before what it caused.** A message and the runs it starts are written by one statement, at the same instant, so a timeline orders events of one instant by kind (message, routing decision, run, ask) before id, and its cursor carries that place.
- **Stored, or worked out now, never mixed.** The runs a message started or joined, the question it answered, the routing decision and the jobs are stored. A run already at work that took the message says so itself (its inbox, or the step where it read it), whoever sent the message there. Why nothing was decided mostly is not: the router's early exits (the workspace paused, the hop limit, no agent to pick from) write no row, and neither does a mention of an agent that doesn't answer the author. An explanation works those out as things are when it is asked and keeps them apart: `skipped`, each agent's `now` and `workspace` describe the present, which may differ from the moment the message was written.
- **`shown` is the app's reading of a run.** `waiting_input` covers waiting for a person, a computer, a plan's limit, a budget and a provider's outage; `shown` tells them apart with the engine's own rules (`computerWaitSql`, `usageWaitSql`, `outageParkedSql`, `passedSql`), and `no_reply` is a run that ended without answering.
- **Where a run ran is not on its row.** `machine` is the computer it waits for, else the one its plan's usage rows name, else its agent's computer now; `from` says which.

Known limits:

- No index serves a run's jobs by their name: the read scans the outbox. An index on `outbox.dedupe_key` with `text_pattern_ops` fixes it when that takes long.
- A run's error code is worked out from its stored text in code. Counting and filtering by code read the range's distinct error texts first, 2,000 at most, most frequent first; past that `more` is true and the rarest are left out.
- A tool result's `durationMs` is null when its call is on an earlier page of steps.

The reads are in `packages/engine/src/operator-runs.ts`, the routes in `apps/server/src/operator/runs.ts`, the tests in `apps/server/test/operator-runs.test.ts`: a history made by posting messages through the app, where everything written says one word that no answer may carry.

## Addendum (2026-11-13): jobs, usage and computers

Three more questions took a database shell: is the queue moving, what did this cost, and is the computer the reason. All are `GET`, additive in `v1`, open to the read-only token, and keep every rule of the two addenda above.

| Method, path | Answer |
| --- | --- |
| `GET /jobs?orgId&kind&status&runId&stuck&from&to&limit&cursor` | The job queue (ADR 0005), every workspace's and the jobs of none, newest first, in keyset pages of up to 200. Each: `id, orgId, kind, status, attempts, maxAttempts, nextAttemptAt, lockedUntil, lockedBy`, the first 300 characters of `lastError`, `createdAt, completedAt`, and for a run's job its `runId` and `cause` (why it woke the run). `runId` keeps the jobs that started and woke one run; `stuck=true` keeps the ones due for over 5 minutes that no worker took and the ones a worker took whose lease ran out. With `summary=true`: `{ at, counts: [{ kind, status, jobs, oldestDueAt }], more, oldestDueAt, oldestDueSeconds }` instead, under the same filters |
| `GET /usage?orgId&agentId&runId&from&to&groupBy&limit` | What model calls spent: `{ from, to, total, groups, more }`, where `total` and each group are `calls, input, output, cacheRead, cacheWrite, costUsd`. Of the whole instance, one workspace, one agent or one run. `groupBy` is `agent`, `day`, `hour`, `model`, `provider` or `payer`, and each group is one row per `billedTo` (`org`, `platform` or `plan`); without it the answer is the total alone. The dates are the last 7 days unless said, 90 days apart at most; for one run they start when it began and have no such limit |
| `GET /orgs/{orgId}/machines` | As §10, and for each computer now also `orgId`, `executors` (what its runner found on it that says its version: `name, version`), `accounts` (its AI accounts: `id, kind, provider, authMethod, plan, status, statusUnknown, shared`, its last success and failure) with `accountCount`, `openTasks`, `holds`, `waitingRuns` and `deletedAt`; and beside the list `provisioning`, how far the workspace's own computer is as a provisioner last said (`state, step, stage, reason, since, requestedAt, expectedReadyAt, specs`), null when nothing was said |
| `GET /machines/{machineId}` | One computer as that list shows it, a removed one too (`deletedAt`): a run's trace may name a computer no longer in its workspace |

What these add to the rules above:

- **A job is never its payload.** A payload holds addresses, links and text: an email's recipient and its link, a push's words. No field of it is read into an answer, not even an id. What a job is about comes from its name alone, and only for a run's job, whose name is written by code as `agent_run.execute:<run id>` and then the word that says why it woke the run. Any other job's name may hold an address and is never returned.
- **A job's last error is cut and masked** like a run's (the addendum above): 300 characters, with anything shaped like a credential replaced.
- **Stuck means what the server itself would tell of.** A pending job due for longer than a lane may stay slow before the server says so (`LANE_SLOW_FOR_MS`, 5 minutes), or a job in a worker's hands past its lease. A job not due yet waits for its time, not for a worker, and is neither stuck nor counted in `oldestDueAt`.
- **Usage is counts.** Tokens by class, calls and cost; the model, the provider and who is billed are names from the catalog and the code. A group is told apart by who it is billed to because a plan's tokens cost nothing here: one sum over both would read as cheap API use.
- **A computer is what runs on it and what waits for it, never how to reach it.** No token or its hash, no connection code, no hostname, no folder, no address it goes out from, none of the folders and tools it allows. Of a background task and of something an agent keeps running there, only how many: their titles, commands, prompts and last lines are what agents and people wrote.
- **A version line is checked before it leaves.** `executors` reads the runner's report by name and returns a version only when it reads as one (letters, digits, dots, dashes, spaces and parentheses); anything else in its place is null, and nothing else of the report comes out (not a sign-in's method or plan, not a reason a capability is off).
- **An AI account is how it signs in and whether it works**, as on an agent (the addendum on lookups): never its email, its label, the organization it belongs to or a hint of its key.

Known limits:

- Only due and leased jobs are indexed. Every other reading of `/jobs`, the counts included, reads the whole outbox, and so does a run's trace for its jobs; `stuck=true` is the cheap one. The outbox keeps its finished jobs, so on an instance with a long history these are for an occasional look, not for polling. Two indexes fix it when that takes long, and neither exists yet: one on `outbox (created_at, id)` for a page, one on `dedupe_key` with `text_pattern_ops` for `runId` and the trace. A page is ordered and continued by the stored `created_at` itself, its cursor carrying the time to the microsecond, because an index on the column serves no expression of it. The counts still read every job in their dates.
- A finished job loses its `lastError` after 30 days (ADR 0005); its row and its name stay.
- `GET /orgs/{orgId}/machines` lists every computer still in the workspace in one answer, as it did, and at most 200 AI accounts across them; `accountCount` says when a computer has more, and `GET /ai-accounts?orgId=` pages them all.
- Usage groups have no cursor: past `limit` groups `more` is true and the dates are to be narrowed.

The reads are in `packages/engine/src/operator-jobs.ts` and `operator-machines.ts`, the routes in `apps/server/src/operator/jobs.ts` and `machines.ts`, the tests in `apps/server/test/operator-jobs.test.ts`.

## Addendum (2026-11-13): one test for every read

Each addendum above has a test of what its own reads leave out. `apps/server/test/operator-canary.test.ts` holds every `GET` of the contract to the same rule at once, the reads of §4, §5 and §10 included, and keeps holding the ones added later.

- **Every read, from the document.** The test takes the `GET`s from the OpenAPI document and fails when one of them has no call, so a read is under it from the day it ships. Every call uses the read-only token; a review block must answer it 403.
- **What people wrote, first.** A workspace's history is made through the app (messages, a tool's input and result, an approval, a question) and the rest is stored beside it: a memory, an agent's instructions, a job's payload with a link, an audit entry's details, a credential, a session, a verification code, a push token, a notification's words, a computer's token and address, a sign-in's email. Each says "canary". No answer may say it, nor a secret the server made itself, nor name a field like a secret; a refusal (400, 403, 404) is read the same way.
- **Then everything else.** Every column of the database that holds text (a string, a list of them, or JSON, where every string inside but an id or a time gets its own) is given a canary that names it, in every row and whatever its table, except the ids a foreign key ties. The reads are called again. What may come back is a closed list in the test (`KEPT`): the names, addresses and handles of §4, an error's first characters, and the kinds, states and codes the server writes. A read that starts returning any other column fails, and the way to make it pass is to add the column to that list, which is a decision someone reads in review.
- **A table the reads query must have rows there.** The test records which tables the reads' statements name and fails when one of them is empty in its history: a column nobody stored anything in proves nothing.

What it cannot see:

- **The events feed's `data` (§5)** is returned whole, so it is on the list whole. What goes into an event is decided where the event is written, and stays the rule of §5.
- **Text changed before it leaves.** The test looks for the canary as written. A value encoded, or cut to a few characters, would pass unseen.
- **A credential inside an error** is covered for one shape (an address with a password, in a run's, a job's and a routing decision's error). The masking is `redactCredentials` (`packages/engine/src/tool-detail.ts`): a credential of a shape it doesn't know leaves with the error's first characters.

## Addendum (2026-11-13): whose tool, and tool calls

"Which tool keeps failing" and "what did it call" were read step by step in one run's trace, or with a database shell across runs. And a tool's name alone doesn't say whose it is: `ask_user` is the server's own word, while a connected server's tool is named by that server and by the workspace that connected it. A caller that shows the first and masks the second had no way to tell them apart. One mark and one read answer both, additive in `v1`, open to the read-only token, under every rule of the addenda above.

| Method, path | Answer |
| --- | --- |
| `GET /runs/{runId}/trace` | As above, and each tool call's and tool result's step now says `builtIn` |
| `GET /orgs/{orgId}/tool-calls?agentId&runId&tool&outcome&from&to&limit&cursor` | The tools the workspace's agents called, newest first, in keyset pages of up to 200: `{ from, to, calls, next }`. Each call: `at`, `runId`, `agentId`, `seq` (its step in the run's trace), `tool`, `builtIn`, `connector` (the connection's label) and `connectorKind` (the service it works in, from the server's catalog: `github`, `gmail`, `postgres`), `outcome` (`ok`, `error`, `refused` or `pending`), `refusal` and `code`, `durationMs` from the call to its result, `inputChars` and `resultChars`. `tool` is part of a name, any case; the dates are the last 7 days unless said, 31 days apart at most, and one run's start when it began with no such limit. With `groupBy=tool`, `agent` or `outcome`: `{ from, to, groups: [{ group, builtIn, calls, errors, refused, pending }], more }` instead, most calls first |

What these add to the rules above:

- **`builtIn` is what the Tool Gateway resolved the name to, kept when it did.** Every call goes through the gateway (ADR 0015), which looks the name up among the run's tools before anything else. When what it finds is one of the server's own tools (no connection behind it, or one of the server's Git tools, which carry a connection only for its credential), the call's step is marked. A connected app's tool is never marked, whatever it is called: a connector's, a mailbox's or a database's name is made of what the workspace named the connection and of what the connected server calls its tools. A name the gateway could not resolve is not marked either, since those are the model's own words. A result's step reads the mark from the call it answers.
- **The mark is stored, not worked out later.** The tools a run has are put together for that run, from its agent's grants and connections at that moment. The same name can be the server's tool in one run and a connected server's in another, so nothing read afterwards could say which it was.
- **A call's outcome is its result's step.** `refused` is a result the gateway itself marked as its refusal (`policy`, `noAccess`, `credential`, `repo`); `error` is any other result that says it failed, a tool's own failure or a call the gateway turned down in words alone (an unknown name, a bad input); `pending` is a call with no result yet, which waits for a person, still runs, or was cut off. A call is paired with the first result after it, in its run, that answers its id.
- **Never the input or the result.** Both are measured in the database, as in a trace. The connection's label is the one text a workspace wrote that comes back, as a trace already returns it; `connectorKind` is the server's own id for the service.
- **Counted by name, a tool is the server's own when any call of that name was.** The same word names the same tool, so one marked call is enough to say the name is the server's.

Known limits:

- A step written before the gateway kept the mark has none: its tool reads as not `builtIn`, the server's own tools included. Nothing stored says what those names were resolved to.
- No index is on a step's time. The read goes through the workspace's runs that were at work in the range (begun before it ends, not ended before it starts) and reads their steps. That holds every call because a call is recorded only while its run is at work: in the run's own turn, or through the runner's bridge, which refuses a run in any other state. A run that waits on a person for weeks is read whole each time.
- Every call in the range is paired with its result before a page or a count is kept, so a long range on a busy workspace is for an occasional look. A call's outcome stored on its own step would let a page read only its own rows.
- Groups have no cursor: past `limit` groups `more` is true and the dates or the filters are to be narrowed.

The mark is written in `packages/engine/src/tools/gateway.ts`, the reads are in `packages/engine/src/operator-runs.ts`, the route in `apps/server/src/operator/runs.ts`, the tests in `apps/server/test/operator-runs.test.ts`.

## Addendum (2026-11-13): connections, the audit log, asks and routines

Four more questions took a database shell: is the connection broken, who changed that, what is the agent waiting on a person for, and did the routine fire. All are `GET`, additive in `v1`, open to the read-only token, under every rule of the addenda above.

| Method, path | Answer |
| --- | --- |
| `GET /orgs/{orgId}/connections?limit&cursor` | What the workspace connected for its agents, removed ones too, newest first, in keyset pages of up to 200: connected apps and servers, mailboxes and databases in one list (`kind`: `connector`, `mailbox` or `database`). Each: `id`, `connector` (the service it is of, as its use is counted, ADR 0103), `label`, `authType`, `status`, `lastErrorCode` and the first 300 characters of `lastError`, `createdAt`, `createdByUserId`, `revokedAt`, `lastUsedDay`, and for a server connected by address `tools`, how many of the tools it lists its workspace set to each level (`read, write, approval, off, undecided`) |
| `GET /orgs/{orgId}/audit?action&actorType&actorId&targetType&targetId&runId&from&to&limit&cursor` | The workspace's audit log, newest first, in keyset pages of up to 200: `{ from, to, events, next }`. Each entry: `id, at, actorType, actorId, action, targetType, targetId`, a tool call's `outcome` (`done`, `failed`, `refused` or `pending`), `runId` and `onBehalfOfUserId`. `action` is how the action's name starts (`connector.`, `tool.call`); the dates are the last 30 days unless said |
| `GET /orgs/{orgId}/asks?kind&open&agentId&runId&from&to&limit&cursor` | What the workspace's agents asked, newest first, in keyset pages of up to 200, in one list: `approval`, `question`, `secret`, `handoff` (a person's turn on an agent's screen) and `consultation` (one agent asking another). Each: `kind, id, status` as stored, `agentId` and `runId` (who asked), `channelId, threadRootId, messageId`, an approval's `tool`, `variant` (a hand-off's `ask` or `takeover`, a consultation's `question` or `note`), `forUserIds` and `forAgentId` (whom it is asked of), a consultation's `answerRunId`, `byUserId` (who decided, answered or took control) and `createdAt, expiresAt, resolvedAt`. `open=true` keeps the ones still waiting |
| `GET /orgs/{orgId}/routines?agentId&limit&cursor` | The workspace's routines, deleted ones too, newest first, in keyset pages of up to 200. Each: `id, agentId, triggerType`, its schedule as stored (`cron`, `timezone`) or the `event` that fires it, `active` and `pausedReason`, `target` (`type, channelId, threadRootId`: where it delivers), `nextRunAt, lastRunAt, createdByUserId, createdAt, deletedAt`, and `runs`, its 5 latest firings, newest first (`id, at, trigger, status, code`, the `runId` it started, `messageId, finishedAt`) |

What these add to the rules above:

- **A connection is what it is of and how it stands, never how to open it.** No credential, wrapped key or token, no OAuth scope or client. No field of where it is or whose it is either: no server address, no account on the other side, no mailbox's address, hosts or login, no database's host, name or user. A server connected by address is told by `connector`, the key its use is already counted under: a preset's id, else its hostname, never a path or a query.
- **A label is the one text a workspace wrote that comes back** from a connection, as an agent's and a channel's names do: it tells two accounts of one service apart. It is what the workspace calls the connection, so it says where one is when nobody named it: the server then calls a mailbox by its address, a database by its host (or by its name, when it is one database of a server), a server connected by address by its hostname, and an app or a server that says whose account it is by the service and that account's name. A caller that masks addresses masks `label`.
- **A last error is cut and masked** like a run's: 300 characters, with anything shaped like a credential replaced. Where the stored error is a single word it is also `lastErrorCode`, since the server writes its own reasons that way (`account_removed`, `already_connected`) and a provider's refusal in words.
- **Tools are counted, never named.** A server connected by address names its own tools, and its workspace decides what each may do. Only how many stand at each level come back; a level the server doesn't know counts as `undecided`, which is how the Tool Gateway treats it. A catalog connector's, a mailbox's and a database's tools are the server's own list, the same for every workspace, so `tools` is null there.
- **An audit entry is who did what to what, never its `details`.** The details hold a tool's input, a file's title, an address, what a setting was changed from and to. They are not read into an answer, not even a named field of them. `action` and `targetType` are the server's own words. `targetId` is an id, except where the target has none of its own and goes by its name, which its workspace may have written: a tool's (`targetType` `tool`), a repository's (`repository`, and `git_repo` for a fetch or a push) and a wiki folder's path (`wiki_folder`). A caller that masks what a workspace wrote masks these four by `targetType`. One of the server's own settings goes by the server's name for it (`instance_secret`). It comes back only when it is one word: anything longer in its place reads as absent.
- **The audit log is read as stored.** A workspace's own reader leaves out the entries a tool writes about itself beside the gateway's `tool.call`; this read returns every row, so one action can show as two.
- **An ask is who asked whom and how it stands, never what was asked.** No approval's title, parameters, reason or result, no question's or consultation's text, choices or answer, no secret's name, label, purpose or site, no words of what a person was asked to do on a screen nor their note. `forUserIds` is whom it is asked of as stored: the people an approval names, else its agent's owner. Who may decide an approval in the end also depends on the workspace's roles and on who covers whom, which this read does not work out.
- **Five tables, one list.** Each kind is read newest first up to the page's size, then the page is cut from them all, ordered by time and then by id as the database orders ids. The same holds for the three tables behind connections.
- **A routine is when it runs and how its firings ended, never what it is told to do.** No name: a routine nobody named is called by its instructions' first line, a reminder always is, and nothing stored tells such a name from one a person gave, so no name comes back; a routine is told by its id. No instructions, no words its schedule was read from nor their description, no stored rule, no list of actions it may take alone; of where it delivers only the kind and the conversation, not whom a reminder is for. A firing is its state, its code and the run it started, never what it reported nor the event that fired it. `cron` and `timezone` come back only when they read as one.

Known limits:

- `lastUsedDay` is counted by service, not by connection (ADR 0103 counts calls under the connector's key): two accounts of one service, or two servers on one host, share it. It is a day, not a time, and only a call counts.
- No index of `agent_questions` or of `secret_requests` starts with the workspace. The read also names the workspace's conversations for the first and its agents for the second, which each table has an index on, so there is a way in that is not the whole table; which one the planner takes on a large instance was not measured. An index on `(org_id, created_at)` of each settles it. Approvals, hand-offs and consultations are found by the workspace.
- The audit log is ordered and continued by the stored time itself, its cursor carrying the time to the microsecond, so its index on the workspace and the time serves a page. A filter that few entries match still reads the range's entries until a page is full: the dates bound it, which is why they default to 30 days.
- A routine whose schedule only its stored rule can say has no `cron`: `nextRunAt` still tells when it runs next.
- GitHub App installations are not rows of their own: the workspace's GitHub connection is listed, and stands for them.

The reads are in `packages/engine/src/operator-workspace.ts`, the routes in `apps/server/src/operator/workspace.ts`, the tests in `apps/server/test/operator-workspace.test.ts`.

## Addendum (2026-11-13): notifications, access, unanswered messages and email jobs

Four more questions took a database shell: was this person told, why can't they see it, which messages did nobody answer, and did the email go out. All are `GET`, additive in `v1`, open to the read-only token, under every rule of the addenda above.

| Method, path | Answer |
| --- | --- |
| `GET /orgs/{orgId}/notifications?userId&kind&from&to&limit&cursor` | One person's notifications in the workspace, newest first, in keyset pages of up to 200: `{ notifications, devices, next }`. Each notification: `id, kind, waiting`, `group` (what its events gather under), `count`, `actors` (who caused it: `type`, `id`), `source` (the ids it points at, by name: `channelId`, `messageId`, `approvalId`, `runId`…), `readAt, doneAt, doneByUser, snoozedUntil, createdAt, updatedAt`, and `push`, the jobs that sent it to the person's devices. `devices`: where their pushes go now (`platform, createdAt, lastSeenAt`). 404 when the workspace or the account doesn't exist |
| `GET /orgs/{orgId}/access?userId&targetKind&targetId` | Whether a person reaches one thing of the workspace as things are now: `{ userId, targetKind, targetId, allowed, rule }`. `targetKind` is `agent` (their message starts a run of it), `channel` or `file` (they read it), `task` (they see it) or `computer` (their agents may use it). `rule` is the step that decided, as a code. 404 when the account doesn't exist, or the workspace has nothing of that kind by that id |
| `GET /orgs/{orgId}/unanswered?channelId&outcome&from&to&limit&cursor` | People's messages no run answered, newest first, in keyset pages of up to 200: `{ from, to, messages, next }`. Each: `id, at, channelId, threadRootId, authorUserId`, `outcome` (why, in the words of `GET /messages/{messageId}/explain`'s `verdict`) and `strategy` (who decided its routing, when a decision was stored). The dates are the last day unless said, 7 days apart at most. With `summary=true`: `{ from, to, counts: [{ outcome, messages }] }` instead, most messages first |
| `GET /email-jobs?to&limit&cursor` | The emails queued to one address, newest first, in keyset pages of up to 200: `{ jobs, next }`. Each is a job as `GET /jobs` lists it, with `template` (which email it sends: `invitation`, `verify_email`, `password_reset`…) and `errorCode` (a provider's refusal as its own code). `to` is the whole address, any case |

What these add to the rules above:

- **A notification is what it tells of and what it points at, never its words.** No snippet of the message, no title, no name of who asked, no reason an agent gave: the column that holds them (`latest`) is not read. Of its `source` only the ids come back, each under the name the server stores it by and only when it is one word; the title stored beside them never does. `kind` and `group` are the server's own names and come back only when they read as one.
- **A push is a job that ran, not a delivery.** `push` lists the notification's first push and the one held back while the person was looking at the app, as jobs. `done` says the job ran and sent to the devices registered then that still wanted it; what the push service answered for each device is not kept. No job means none was queued: no device, the person's own choice for that kind, or read before. `devices` is the person's, not the workspace's, and is a platform and two times: never what a push is sent to.
- **Access is the app's own check, with a rule that retells it.** `allowed` is what the server's own check answers for that person now: the function or the condition the apps' own requests go through (`canTalkTo`, `channelReaderSql`, `taskSeenSql`, `fileSeenSql`, `mayUseDevice`). `rule` goes through the same steps in order to name the one that decided. Where the two disagree, the answer stays the check's and the rule reads `unknown`, so a rule that fell behind the check never turns a no into a yes.
- **Outside the workspace, nothing is reached.** Someone who isn't a member (`not_a_member`), an account blocked or being deleted (`account_closed`) and a suspended workspace (`workspace_suspended`) answer no before the thing's own rule is looked at.
- **Unanswered is what an explanation says, for a range of dates at once.** A person's message is listed when it started no run, was taken by none already at work and answered no agent's question, which are the three verdicts of an explanation that name a run (`run`, `joined`, `answered_question`). `outcome` is the verdict an explanation would give it from what is stored, worked out in one statement for the whole range. A test asks both for the same messages and holds them to the same answer.
- **An address finds its emails and never comes back.** `to` is compared inside the database with the addresses each `email.send` job is to. Of a job's payload only the template's kind is read into an answer: never an address, a subject, a link, a code or a name. `lastError` is cut and masked as in `GET /jobs`.

Known limits:

- No index covers one person's notifications whatever their state (the inbox's own are for the open ones and the done ones apart), so the read goes through the workspace's. An index on `(org_id, user_id, created_at)` settles it.
- A reminder's push and a snooze's wake are jobs named by a time: they are not under their notification, and `GET /jobs?kind=push.send` lists them. The person's choices of what pushes them are not in the answer.
- Access is as things are now, not as they were when something happened. It answers one question per kind: talking to an agent, not seeing how it works; reading a channel, not posting in it nor calling agents there (a channel's exceptions decide those). A phone reached through a computer, a wiki page and an AI account are not kinds it knows.
- What the router's own exits don't store reads `not_routed`, as in an explanation, whose `skipped` says more for one message. A message people wrote to each other is listed too. An agent that answered a message while answering a later one is not known.
- To tell that a run already at work took a message, each candidate is compared with the runs of its conversation from the day before. No index of `agent_runs` starts with the workspace and the conversation, which is why the range is 7 days at most. One on `(org_id, channel_id, created_at)` settles it.
- Like `GET /jobs`, the email read goes through the whole outbox. A finished job keeps its payload 30 days, so an older email is not found by its address; the job of a code to type in is deleted once it is sent or given up. `errorCode` is read from how the server words a provider's refusal, the status and the name in brackets, and is null for an error worded another way. What happened after a provider accepted an email (delivered, bounced) is the provider's to say.

The reads are in `packages/engine/src/operator-people.ts`, `operator-runs.ts` (unanswered) and `operator-jobs.ts` (email jobs), the routes in `apps/server/src/operator/people.ts`, `runs.ts` and `jobs.ts`, the tests in `apps/server/test/operator-people.test.ts`.
