# 0075. Limits on public routes, and agentes.chat Cloud's bot check

- Status: Accepted (built: server, web, the shared client and the phone app)
- Date: 2026-10-27
- Code: `apps/server/src/http/client-ip.ts` (`TRUSTED_PROXIES`), `packages/adapters/src/rate-limiter.ts` (`limitIp`, `release`), `packages/adapters/src/human-check.ts` (Turnstile), `apps/server/src/http/human-check.ts`, `apps/server/src/http/human-pass.ts`, `apps/server/src/auth.ts` (the hooks, the email caps, the wrong passwords, sign-ups on registered hosts), `apps/server/src/routes/app/account.ts` (the email lookup), `apps/server/src/start.ts` (the boot probe), `apps/server/src/operator/orgs.ts` (`/health`), `packages/client/src/lib/human-check.ts`, `apps/web/src/lib/human-check.tsx`, `apps/web/public/human-check.html`, `apps/mobile/src/features/auth/HumanCheck.tsx`, `apps/mobile/src/features/auth/human-check.ts`

## Context

Every route a signed-out person reaches has a limit per IP, but the key was the whole address: an IPv6 /64, which one customer usually holds, gave 2^64 fresh counts. Reset and confirmation emails had no cap per address, so a mailbox could be flooded from many addresses. Behind a public proxy, our own limits counted every request as the proxy's. And agentes.chat Cloud, open to anyone, wants a bot check in front of its forms that most people never see, while self-hosted servers keep nothing of it.

## Decision

1. **Per IP means IPv6 by its /64** (`limitIp`), as Better Auth counts its own: sign-in options, the ask and its code, the waiting list, a new invitation, a computer's pairing and its host sync, desktop and native downloads. The address a pairing records stays whole.
2. **`TRUSTED_PROXIES` counts for our limits too.** Walking `x-forwarded-for` from the right, its addresses and ranges are skipped like internal hops. An entry that isn't an address or a range is skipped.
3. **Reset and confirmation emails: at most 3 an hour per address** on the main address, and 3 more across all registered hosts together (point 5). More go nowhere, and Better Auth answers the same, so nothing tells whether an email went out. Counted in each server process's memory, like Better Auth's own counts per IP, so a restart starts them again and behind a load balancer each process allows that many.
4. **The bot check is Cloudflare Turnstile, on only with both `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`.** Half a pair stops the server at boot. Without them there is no script, no widget, no check and no request to Cloudflare. Both descriptions start "For agentes.chat Cloud. Unset by default." It is public code switched on by env vars (ADR 0002).
5. **Six actions:** email lookup, sign-in, sign-up, password reset, the code to ask to join (ADR 0072), the waiting list. The widget is Managed with `appearance: interaction-only`: a checkbox shows only when Cloudflare doubts someone. The token travels in `x-captcha-response`. Each route checks it after its per-IP limit and before any count people share, such as a link's or the whole server's, so refused bots don't spend those. Better Auth's hook runs after Better Auth's own limits, and sign-up checks it before its policy. A host registered under ADR 0194 runs no check but the waiting list's, so there the per-IP limits, tighter (point 11), guard the counts people share, and the counts per address (the emails of point 3, the wrong passwords of point 10) are kept apart: every registered host's requests share one count of their own per address, so unchecked traffic never spends what the main address's people share.
6. **Our own siteverify call**, an adapter. A missing or refused token is a 403 `human_check`. A token counts only for its action, seen on `PUBLIC_URL`'s host, except the answers of Cloudflare's test keys. One retry, with the same idempotency key, on no answer within 5 s, a 5xx or `internal-error`. Cloudflare out of reach lets the request through, logged: nobody is locked out by someone else's outage, and every limit still holds.
7. **A page that can't make a token** (the script didn't load, the widget failed, nothing in 30 s) sends `unavailable`, with Turnstile's error code when it gave one. It goes through only while this server can't reach Cloudflare either, asked again at most once a minute: the dummy token to siteverify and the widget's script. Otherwise it is a 403 `human_check_blocked`, read as "The check didn't load. Try another browser or network.", which doesn't blame the browser, since a widget down while siteverify answers looks the same from here. Turnstile's codes for a wrong site key or a host it doesn't allow (110100, 400020, 110200) are logged, at most once a minute, since any client can send them.
8. **A wrong key never fails quietly.** At boot, a secret Cloudflare refuses stops the server with the variable's name. One of Cloudflare's test secrets (they refuse real tokens, and the one that passes takes a public dummy token from anyone) starts it with a warning naming `TURNSTILE_SECRET_KEY`, since a test server runs one on purpose. While running, a refused secret lets requests through, logged. The operator API's `/health` reports `botCheck`: `state` (`off`, `ok`, `unreachable`, `secret_refused`), `since` when it took that state, `blocked`, the networks refused `human_check_blocked` in the last 10 minutes, `passed`, the tokens Cloudflare passed in those minutes, and `testing`, true with a test secret. `blocked` counts each network once, an IPv4 address or an IPv6 /64, because any client can claim its page couldn't load the check. Such claims can raise `blocked` but never lower `passed`, and a widget down for everyone does both. An operator's monitoring can raise its alerts from it, since a line in the server's log reaches nobody.
9. **The apps.** `auth-config` gives `turnstileSiteKey`. The web adds `api.js?render=explicit` once, from the first page that checks (the landing waits for a field's first focus), renders a widget per form and action, sends its token, resets the widget after every call, and tries once more on `human_check`, never on `human_check_blocked`. While Cloudflare asks for a click, a call waits for the person. A card that leaves the checkbox less than 300 px gives it room under 480 px, and a place still narrower takes the `compact` widget. The phone runs the same widget in a hidden WebView on this server's `/human-check.html`, so the host is ours, and reads its events there. Its `originWhitelist` holds the server's origin and `https://challenges.cloudflare.com` beside `about:blank` and `about:srcdoc`, since react-native-webview sends an address outside it to the browser, frames included. The library reads each entry only as the start of an origin, which `https://app.agentes.chat.evil.example` passes, so `onShouldStartLoadWithRequest` loads only those exact origins, and the app reads messages only from the server's page. When Cloudflare wants a click while a call waits, the same WebView rises as a sheet with Cancel, which ends the call quietly. Under 352 pt the checkbox spans the sheet, so its 300 px fit. Its blocked line names no browser: "The check didn't load. Try another network." A page that didn't load loads again at the next press, so another network helps at once.
10. **Wrong passwords per account.** Only a password sign-in refused for its credentials counts: a wrong password, or an address nobody has, which Better Auth refuses alike (`INVALID_EMAIL_OR_PASSWORD`), so the count never tells whether an account exists. A sign-in that succeeds counts nothing and clears nothing. Each failure counts twice, keyed by the address in lower case, hashed: for the address from the sender's network (as the per-IP limits take it, point 1), at most 10 in 15 minutes, and for the address from all networks, at most 50 in 15 minutes, both through the `RateLimiter` in each server process's memory, so a restart starts them again and behind a load balancer each process allows that many. Past the first, that network is refused for that address until its window opens again; past the second, every network is. A count every sender shares is one anyone can spend (ADR 0072): with only the second, ten requests with someone's address from one network would lock the person out; with the first in front, one network spends only its own tries, and locking an address out for everyone takes failures from five networks or more. The refusal is a 429 `TOO_MANY_PASSWORD_TRIES` with `Retry-After`, the right password included, and the same seconds as `retryIn` in its body (the wait until both counts take a try again, when both are full), since the apps' Better Auth client reads the body and not the headers. A try is taken before the password is checked and given back (`RateLimiter.release`) when the sign-in ends any other way than refused for its credentials, a server error included (Better Auth then skips its after hooks, so the handler around it gives the try back), and a try either count refuses gives back what it took, so tries in flight can't all pass a count none of them wrote yet, and a network's refused tries never spend the count from all networks. Counted after the bot check, so a refused bot spends none of an account's tries (point 5); the main address and the registered hosts each keep their own two counts (point 5). It bounds guessing on one account, not one guess each over many accounts, which Better Auth's limit per IP (10 sign-ins a minute, unchanged) and the bot check bound. The apps say that this account has had too many password tries and in how many minutes to try again, never that the password was wrong.
11. **What the bot check no longer guards on registered hosts.** Nothing ties an account to a host, so every account's email lookup, password sign-in and password reset can be asked on any registered host, where no bot check runs (ADR 0194). On a server with registered hosts, the main address's bot check therefore no longer stands between a script and those calls for any account: what guards them is the limits per network and per account, and sign-up there can send confirmation emails with only the limit per network in front of it. So the limits per network are tighter there, counted for all registered hosts together, apart from the main address's, in each server process's memory like the others: the email lookup at most 10 in 10 minutes per network (30 on the main address), and sign-up at most 5 in 15 minutes (Better Auth's 10, which holds everywhere, on the main address), counted in Better Auth's hook through the `RateLimiter`. Past either, a 429 with `Retry-After`.

## Consequences

- A self-hosted server without the keys loads nothing from Cloudflare and checks nothing. Its limits now count IPv6 by /64 and walk past its trusted proxies.
- The Cloud sets the keys only once the phone build with the check is in both stores, the desktop release keeps Turnstile's frame in its window, the privacy policy names Cloudflare, and control's alerts read `botCheck`. Turning the check off is unsetting both keys and starting the server again without them.
- An outage that breaks only Cloudflare's widget, while siteverify still answers this server, refuses people with "The check didn't load": `blocked` rises while `passed` falls. The way out is to turn the check off.
- Better Auth's counts per IP, the email caps, the wrong passwords per account and the registered hosts' limits of point 11 reset on a restart and are kept per process. The per-address limits of ADR 0072 don't.

## Alternatives considered

- Better Auth's captcha plugin: it fails closed (a 500 when siteverify is down), takes one action for every path, calls Cloudflare in tests, and can't guard our own routes.
- Turnstile's invisible mode: a person Cloudflare doubts would have no way through.
- Exempting the phone app: every bot would claim to be it.
- Siteverify in a private Cloud service: it hides about 50 lines and adds a hop that can fail, and the widget's code stays public anyway, in the web and phone apps.

## Addendum (2026-11-13): tokens made on the landing page

The landing page is a site of its own (`LANDING_URL`). Its forms, the waiting list and the partner program's (`/api/partners/waitlist`), both check the action `waitlist`. Point 6 counted a token only when Cloudflare saw it on `PUBLIC_URL`'s host, so every token the landing page made was refused, and with the check on nobody could join from there.

A token made on `LANDING_URL`'s host now counts too, for `waitlist` only. One made there for email lookup, sign-in, sign-up, password reset or the code to ask to join is refused: the landing page is other code on another site, and its tokens never stand for the app's forms. Without `LANDING_URL`, only `PUBLIC_URL`'s host counts, as before, and there is no waiting list. The widget in Cloudflare's dashboard lists both hosts. A host it doesn't list fails on the page with 110200, logged as point 7 says.

The landing page runs the widget as point 9 says for the web: `api.js?render=explicit` once, on a field's first focus, Managed with `appearance: interaction-only`, the token in `x-captcha-response` (its CORS allows that header), a reset after every call, one more try on `human_check` and never on `human_check_blocked`, and `unavailable`, with Turnstile's error code, when no token comes within 30 s.

Not chosen: one list of hosts for every action. A token made on the landing page would then count for a sign-in too.

## Addendum (2026-11-13): one check for one sign-in

Signing in with a password is two guarded calls, the e-mail's lookup and the password, each with a token made for its own action (point 5). On the phone, where the widget runs in a WebView and Cloudflare asks for a click far more often than in a browser, the person met the checkbox twice in a row: once after their e-mail, once after their password.

The lookup that passes the check now answers with a **pass** (`pass` in its answer). The step that follows it for the same address, sign-in, sign-up or password reset, sends the pass in `x-captcha-response` where the token goes, and the server takes it in the check's place. The apps send it first and ask the widget only when the server refuses it (`withHumanCheck`'s `pass`), so a pass that ran out costs one more request and nothing else.

A pass is `pass.<expiry>.<signature>`, an HMAC under a key of its own derived from `AGENTES_SECRET` (`human-pass`), over the expiry, the address in lower case and the network (an IPv4 address or an IPv6 /64, as point 1 counts). It counts:

- for that address only, from that network only, for ten minutes;
- for five calls, counted in memory like the counts of point 3 (a restart gives a pass its calls back, never more time);
- never for the lookup itself, the code to ask to join or the waiting lists. Every sign-in starts with a real check, and one check opens one address.

A pass that doesn't count is a 403 `human_check`, like a refused token. Without the keys there is no check and no pass. Every limit per IP and Better Auth's own counts hold as before.

What it gives up: a token per password try. Someone who solves one check may now try five passwords on that one address before the next check, within Better Auth's limit per IP. Guessing across addresses still costs a check per address, since each needs its own lookup.

Whether the checkbox shows at all is Cloudflare's call (Managed, `interaction-only`), not this server's. A widget that never shows one is a choice in Cloudflare's dashboard (its non-interactive mode), with point 5's caveat: whoever Cloudflare doubts then has no way through.

Not chosen: a pass kept on the device for weeks (one solved check would open sign-ins from anywhere for as long), and one token for both actions (Cloudflare spends a token on its first siteverify).
